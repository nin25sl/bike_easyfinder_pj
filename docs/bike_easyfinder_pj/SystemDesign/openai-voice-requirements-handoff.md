# OpenAI音声会話用 MVP要件引き継ぎ

> **目的とゴールの違い**
>
> - **目的** = Why（なぜ音声会話へ引き継ぐか）
> - **ゴール** = Done 条件（どの判断がテキストとして残れば完了か）

## 目次

<inline-toc preview="3"></inline-toc>

## 目的

ChatGPT iOSの音声会話で、Bike EasyFinderのMVP要件、承認待ち事項、先行実装との差分を順番に確認し、プロダクトオーナーの判断を構造化されたテキストとして残す。

## 背景

RD-01〜RD-04は承認済み。RD-05は否認・再検討、RD-06はRD-05反映と全体API整理後に再検討、RD-07は修正反映・再レビュー待ち、RD-08とRD-11は条件付き承認、RD-10とRD-12は修正条件付き承認である。RD-09は統合要件定義書に再設計案を記載している。要件確定後に基本設計を作成するため、先行実装をそのまま正とせず、承認済み要件と基本設計を基準に改修範囲を決める必要がある。

音声会話の文字起こしは逐語記録にならない場合がある。そのため、音声だけで承認を完了せず、会話終了時に決定事項をテキストで復唱し、プロダクトオーナーが最終確認する。

## ゴール

- RD-05〜RD-07の修正版を再確認し、RD-08〜RD-12を順番に説明して承認・修正・保留を記録する。
- A-01〜A-04を一件ずつ確認する。
- 要件、基本設計、実装の境界を混同しない。
- 音声会話終了時に、Codexへ渡せる決定記録を生成する。

## 本文

### 1. ChatGPTへの最初の指示

以下を音声会話開始前のテキストメッセージとして使用する。

```text
GitHubの nin25sl/bike_easyfinder_pj リポジトリを参照してください。

最初に次の順番でファイルを読んでください。
1. docs/bike_easyfinder_pj/SystemDesign/openai-voice-requirements-handoff.md
2. docs/bike_easyfinder_pj/SystemDesign/mvp-requirements-v1.md
3. docs/bike_easyfinder_pj/SystemDesign/mvp-openapi-v1.yaml
4. docs/bike_easyfinder_pj/SystemDesign/mvp-requirements-decision-backlog.md

読了後、まだレビューを開始せず、参照できたファイル名と現在の承認状態だけを簡潔に回答してください。
その後、同じチャットで音声会話を開始します。
```

### 2. プロジェクト概要

- プロダクト: 利用可能時間と興味から、時間内に往復できるバイクツーリング先を提案するiPhoneアプリ。
- 初期テスト: 福岡市および周辺のSpot 100件程度。
- MVP公開地域: 九州7県。固定件数より継続収集・更新基盤を優先する。
- MVPの検証対象: 検索ではなく提案される体験が、目的地決定と走行開始につながるか。
- 対象外: 内蔵ターンバイターンナビ、Android、オフライン地図、UGC、SNS、ML・LLM推薦。
- 走行開始後: Apple Mapsへ引き渡す。

### 3. 承認済み事項

RD-01〜RD-04は2026-09-23にプロダクトオーナー承認済み。音声会話では、明示的な変更依頼がない限り再承認を求めない。

#### RD-01 検証仮説・KPI・リリース

- TestFlight限定β。
- 30人、4週間、有効推薦セッション100件。
- 主要KPIは `route_started / recommendation_view`。
- 20%以上で成功、10%以上20%未満で再検証、10%未満で中止候補。

#### RD-02 ユースケース

- 仕事終わり2時間、休日午前4時間、目的指定の3ケース。
- 必須入力は現在地、利用可能時間、興味、高速利用可否。
- 現在地へ戻る日帰り往復に限定する。

#### RD-03 MVP境界

- 候補最大5件、詳細、地図、フィードバック、Apple Maps連携。
- アカウントなし、匿名端末ID。
- アプリの責任は目的地の引き渡しまで。

#### RD-04 モバイル・地図・ナビ

- iPhone、iOS 17以上、SwiftUI、MapKit、CoreLocation。
- 位置権限は `When In Use` のみ。
- 外部ナビはApple Mapsのみ。

### 4. RD-05〜RD-12の状態と決定案

詳細は要件定義書を正とする。以下は音声レビュー用の要約。

#### RD-05 UX

- 状態は否認・再検討。候補一覧ではなく、最大5件を1件ずつカードで提案する更新案とする。
- `興味あり / 興味なし / 行ったことがある` を記録し、興味あり一覧から後で確認できるようにする。
- 初回は説明と条件設定、2回目以降は前回条件の再利用・変更・興味あり確認から開始する。
- 位置拒否、候補0件、部分障害、全障害を別状態として扱う。
- スワイプを必須にせず、VoiceOverとDynamic Typeへ対応する。

#### RD-06 推薦・API

- 状態は再検討。最初にアプリ全体、API一覧、責務、画面対応を示し、その後に個別OpenAPIを確認する。
- 公開APIはRecommendation、Interaction、Privacyの3領域とし、Spot Query、移動時間推定、推薦ルールはRecommendation内部の責務とする。
- 合計時間は往路、滞在、復路、帰着余裕の合計。
- 帰着余裕は15分と走行時間の10%の大きい方を5分単位で切り上げる。
- 興味なし・訪問済みは今後の推薦から基本的に除外する。
- APIの個別契約の正本は `mvp-openapi-v1.yaml` とし、RD-05反映後に再承認する。

#### RD-07 Spotデータ

- 状態は修正反映・再レビュー待ち。
- 初期テストは福岡周辺100件程度、MVP公開は九州7県を対象に継続収集・更新基盤を構築する。
- 候補発見は公開Webの幅広い情報源を利用できる。変動情報は施設・道路管理者・自治体等の信頼できる情報源で確認する。
- 1Spotに複数カテゴリを許可し、正式taxonomyは実データ収集・分析後に確定する。
- 説明、出典、特徴、位置、分類語など再分類に必要な原情報を保存する。
- 月次自動更新を基本とし、自動確認不能・矛盾・低信頼データだけ人間がレビューする。
- Google PlacesはMVP不採用。

#### RD-08 スキーマ

- PostgreSQL + PostGIS、UUID、`GEOGRAPHY(Point, 4326)`。
- Canonical SpotとSourceを分離し、属性単位で出典を追跡する。
- 重複候補は100m以内かつ名称類似度0.8以上とし、手動承認する。

#### RD-09 移動時間推定・外部Map連携

- 現行のValhalla中心案は否認・再設計とする。
- Bike EasyFinderは行き先を提案し、推薦に必要な距離・所要時間だけを取得する。
- 実際のルート検索・ナビはApple MapsまたはGoogle Mapsへ委譲する。
- Apple MapKit、Google Routes API、その他APIを精度、料金、iOS親和性、制約で比較する。
- POCは九州7県で行い、都市部、山間部、海沿い、高速利用を含める。
- Valhallaは独自のバイク向けルート生成が必要になった段階で再評価する。

#### RD-10 天気・道路情報

- 修正条件付き承認。WeatherKitは天候依存Spotの詳細画面における注意情報取得に限定し、推薦ランキングと候補除外には使用しない。
- 天候依存属性は `sunny_recommended`（晴れ向き）から開始し、将来拡張可能な複数値形式とする。属性付与方式とポップアップ発火条件は別途決定する。
- リアルタイム道路規制とJARTIC統合は、MVPおよび将来版のアプリ側対象外とする。
- 実際の道路状況、通行可否、走行ルートはApple Maps／Google Maps／現地標識を優先し、外部Map遷移前に安全確認を表示する。
- 最終確認時刻はユーザー画面に表示せず、Freshnessは内部管理する。

#### RD-11 プライバシー

- 状態は条件付き承認。MVPはアカウントなし・匿名installation IDで進め、将来user IDへ紐付け可能なデータモデルにする。
- 課金、Web版、複数端末同期、履歴引き継ぎはMVP後のスコープとする。
- 利用分析は全ユーザーを基本対象とするが、初回に目的を明示して同意を取得し、設定から撤回できるようにする。
- 分析はATT不要の自社サービス改善に限定し、広告・クロスアプリトラッキングには使用しない。
- 正確な現在地は推薦処理中だけ利用し、保存しない。
- MVPで削除トークン方式による匿名データ削除を提供し、installation IDに紐づく生データを削除可能にする。
- 保持期間は全データ棚卸し後にデータごとに決め、実装完了時にApp Store Connect申告を再棚卸しする。

#### RD-12 基本設計・運用

- 状態は修正条件付き承認。Valhallaと独自ルーティングをMVP構成から外し、推薦用所要時間推定と外部Mapへのナビ委譲を前提とする。
- local、staging、productionの3環境とし、stagingとproductionは同一アーキテクチャ、環境固有値は環境差分一覧で管理する。
- 推薦API p95 5秒以内、初回候補表示3秒程度を暫定目標とし、CPU、メモリ、DB負荷、API応答時間、エラー率、コストを監視する。
- 日次バックアップ、7世代以上保持、月1回リストア試験を行い、対象データと復旧優先度を基本設計で確定する。
- 外部API・インフラ費は月額1万円以内。常時高スペックや不要なサービスを避け、実測使用量に応じて拡張する。
- 福岡100件やValhalla POCをリリースゲートにせず、九州7県で候補取得、外部Map遷移、県別実機確認、継続収集、Privacy、品質、監視・復旧・費用管理が成立することをVer0.1の条件とする。

### 5. 必ず確認する4件

以下を一件ずつ説明し、プロダクトオーナーが回答するまで次へ進まない。

#### A-01 データ保持期間

- 決定: 一律の保持期間は設けず、全保存データを棚卸しした後、利用目的・保存場所・削除条件・第三者送信と合わせてデータごとに決定する。
- 状態: 方針承認済み。具体的期間は棚卸し後に個別承認する。

#### A-02 月額上限

- 決定: MVPの外部API・インフラ合計を月額10,000円以内とする。超過する変更は再承認する。
- Apple Developer Program、開発端末、ドメインは別管理。
- 状態: 承認済み。

#### A-03 天気・道路情報

- 状態: 修正条件付き承認。
- 残条件: 天候依存属性の付与方式、注意ポップアップ発火条件、WeatherKit取得失敗時文言、ナビ移行前の天気注意再表示の要否を確定する。

#### A-04 移動時間推定・外部Map連携

- 現行案は否認済み。Apple MapKit、Google Routes API、その他APIの比較結果、許容誤差、九州7県POC件数、外部Map未導入時UXを整理して再提示する。
- 選択肢: 再設計案を承認、変更、保留。

### 6. 音声レビューの進め方

音声会話を開始したら、ChatGPTは次の順序を守る。

1. 日本語で話す。
2. 最初に30秒程度でプロジェクトと承認状態を要約する。
3. RD-05〜RD-07の修正版を再確認した後、RD-08からRD-12を一件ずつ説明する。
4. 各RDについて「承認」「修正」「保留」の回答を求める。
5. 一度に複数の判断を質問しない。
6. ユーザーの回答が曖昧な場合は、承認と推測せず確認する。
7. A-01〜A-04を必ず個別に確認する。
8. 実装方法の細部は、要件判断に必要な場合だけ説明する。
9. 先行実装を理由に要件を固定しない。
10. 会話終了前に決定結果をテキストで復唱する。

### 7. 音声での開始文

ChatGPTは次の内容から開始する。

```text
Bike EasyFinderの要件レビューを始めます。
RD-01からRD-04は承認済みです。RD-05は否認・再検討、RD-06は再検討、RD-07は修正反映・再レビュー待ちです。
今回はまずRD-05からRD-07の修正版を確認し、その後RD-08からRD-12と、データ保持期間、月額上限、天気と道路情報、移動時間推定・外部Map連携の4件を確認します。
一度に一つずつ説明し、承認、修正、保留のいずれかを確認します。
まずRD-05のカード型提案フローの修正版から始めてもよいですか。
```

### 9. Codexへの戻し方

音声会話で生成した決定記録を、同じGitHubリポジトリのIssue、またはCodexのチャットへ貼り付ける。Codexには次のように依頼する。

```text
以下の要件レビュー決定記録を正として、
mvp-requirements-v1.md、mvp-openapi-v1.yaml、
mvp-requirements-decision-backlog.mdを更新してください。
変更後に要件間の矛盾を検査し、基本設計へ進める状態か報告してください。
```

### 10. 禁止事項

- 音声会話だけを最終承認記録にしない。
- ユーザーが明示していない判断を承認扱いにしない。
- `.env`、APIキー、削除トークン、正確な現在地を会話やGitHubへ貼らない。
- garbage内の旧文書を現行要件として扱わない。
- 先行iOSコードを承認済み基本設計として扱わない。

- 音声会話の文字起こしと、実際の発言が完全に一致しない可能性があるため、最終テキストを必ず確認する。
