# バイク目的地提案アプリ MVP 要件定義書 v1

> **目的とゴールの違い**
>
> - **目的** = Why（なぜこのMVPを実施するか）
> - **ゴール** = Done 条件（何を満たせば要件定義完了とするか）

## 目次

<inline-toc preview="3"></inline-toc>

## 目的

九州7県のiPhoneユーザーが、検索や一覧比較に時間を使わず、「今から使える時間」と興味に合う日帰りツーリング先を提案から決められるかを、最小の製品で検証する。データ・機能の初期テストは福岡周辺から開始するが、MVP公開対象地域は九州7県とする。

本書はRD-01〜RD-12の決定を一つに統合し、今後作成する基本設計書、データ契約、実装、試験、限定β判定の基準とする。

## 背景

既存サービスは検索型・地図型が中心であり、ユーザー自身が候補を比較して時間内に帰れるかを判断する必要がある。本MVPは目的地検索ではなく、現在地、利用可能時間、興味、高速道路利用可否、過去のリアクションから、時間内候補を1件ずつカードで提案する。

価値検証前に内蔵ナビ、Android、オフライン地図、高度な個人化を実装すると、主要仮説と関係の薄い開発・運用コストが増える。そのため、iOS限定βと外部ナビ連携に責任範囲を絞る。

## ゴール

- 対象ユーザー、検証仮説、KPI、成功・再検証・中止基準が一意である。
- 主要ユースケース3件と、位置拒否、候補0件、外部障害を含む受入条件がある。
- MVP対象、対象外、外部ナビとの責任境界が明確である。
- 初回と2回目以降の画面フロー、カード型提案、リアクション、興味あり一覧の主要状態が確定している。
- MVP全体のAPI一覧と責務・画面対応を確認したうえで、推薦ルール、時間計算、API v1、エラー・タイムアウト契約が確定している。
- 九州7県の継続収集、Source/Freshness、複数カテゴリ、匿名行動イベントの論理スキーマが確定し、taxonomyの確定手順が定義されている。
- 地図、移動時間推定、外部Map連携、天気、道路情報、外部POIの採否と利用条件がある。
- 位置情報、行動データ、同意、保存期間、削除、App Store申告方針がある。
- 基本設計へ渡す構成、非機能要件、費用上限案、実装順、リリースゲートがある。
- 未決事項に責任者と決定期限がある。

### 2. 対象ユーザーと検証仮説（RD-01）

#### 2.1 対象ユーザー

- 九州7県から日帰りツーリングをするiPhoneユーザー。初期テストの募集は福岡市および周辺を優先する。
- 仕事終わりや休日に2〜4時間程度走りたいが、行き先決定を負担に感じる人。
- 年齢、車種、排気量、経験年数による利用制限は設けない。
- 排気量別の道路制約はMVPで扱わないため、原付・125cc以下向けの経路保証は行わない。

#### 2.2 解決する場面

「走れる時間は決まっているが、検索・比較して行き先を決めるのが面倒」という出発前の場面を解決する。走行開始後の経路案内は外部ナビの責任範囲とする。

#### 2.3 検証仮説

> 九州7県のiPhoneユーザーにとって、検索結果を自分で比較するより、利用可能時間、興味、過去のリアクションから時間内候補を1件ずつ提案される方が、短時間で目的地を決めて出発しやすい。

### 3. リリース形態、KPI、判定（RD-01）

#### 3.1 リリース形態

- TestFlightによる招待制限定β。
- 募集人数30人、検証期間4週間。
- 有効推薦セッション100件を最小判定母数とする。
- 4週間で100件に満たない場合は最大2週間延長する。
- App Store一般公開は限定βの継続判断後に別途承認する。

#### 3.2 主要ファネル

```text
recommendation_view → spot_selected → route_started
```

- `recommendation_view`: 候補が1件以上表示された推薦セッションごとに1回。
- `spot_selected`: 同一セッションで「ここに行く」が押された場合に1回。
- `route_started`: Apple Mapsへの引き渡し要求が成功した場合に1回。
- 同一セッション内の再試行は各転換率へ重複計上しない。
- 候補0件、位置権限拒否、API失敗は主要ファネルの分母から除外し、品質指標へ計上する。

#### 3.3 成功基準

| 指標 | 成功 | 再検証 | 中止候補 |
|---|---:|---:|---:|
| `spot_selected / recommendation_view` | 35%以上 | 20%以上35%未満 | 20%未満 |
| `route_started / recommendation_view` | 20%以上 | 10%以上20%未満 | 10%未満 |
| 候補表示成功率 | 95%以上 | 90%以上95%未満 | 90%未満 |
| 候補表示時間 p95 | 5秒以内 | 8秒以内 | 8秒超 |

- 成功: 主要KPIを満たし、重大な安全・データ品質問題がなければ継続する。
- 再検証: UX、候補品質、募集導線を分析し、2週間以内の改善実験を1回行う。
- 中止候補: 有効100セッション以上で `route_started` が10%未満、かつインタビューでも価値が支持されない場合は拡大を止める。
- 安全上の重大問題、データ利用条件違反、運用不能が判明した場合は母数に関係なく停止する。

### 4. ユースケースと共通業務ルール（RD-02）

#### 4.1 共通ルール

- 出発地と帰着地は現在地とし、同一地点へ戻る日帰り往復に限定する。
- 必須入力は現在地、利用可能時間、興味、高速道路利用可否。
- 興味は1件以上選ぶ。`おまかせ` を選んだ場合は他の興味を同時選択しない。
- 利用可能時間は `1時間 / 2時間 / 3時間 / 4時間 / 半日（6時間） / 1日（10時間）`。
- 任意出発地点、帰着時刻、排気量、給油・食事の旅程組込みはMVP後とする。
- 1推薦セッションで条件を満たす候補を最大5件用意し、画面には1件ずつ表示する。件数を埋めるために時間条件を自動緩和しない。

#### 4.2 UC01 仕事終わりに2時間走る

1. 「現在地から探す」を選択する。
2. 位置情報を許可し、2時間、興味、高速利用可否を入力する。
3. 2時間内の提案を1件ずつ確認し、`興味あり / 興味なし / 行ったことがある` のいずれか、または詳細表示を選ぶ。
4. 行きたい提案の詳細から「ここに行く」を選び、Apple Mapsへ目的地を渡す。

#### 4.3 UC02 休日午前に4時間走る

UC01と同じ導線で利用可能時間を4時間とする。時間内の候補について、興味一致だけでなく候補の特徴が偏りすぎないようにする。

#### 4.4 UC03 目的を指定して走る

画面用の暫定的な興味選択肢から1件以上を選び、一致した特徴と推薦理由を候補へ表示する。興味選択肢とデータ分類の対応は、実データ分析後にtaxonomy v1として承認する。

#### 4.5 共通例外

| 例外 | 期待動作 |
|---|---|
| 位置権限未決定 | 「現在地から探す」を押した時だけ `When In Use` を要求する |
| 位置権限拒否 | 必要理由、再試行、設定アプリへの導線を表示する |
| 位置取得失敗 | 再試行を表示し、前回位置を無断利用しない |
| 候補0件 | 時間、興味、高速可否の変更導線を表示する |
| 推薦API失敗 | 再試行可能なエラーを表示し、古い結果を新規結果として表示しない |
| 一部経路失敗 | 失敗候補を除外し、残る候補と警告を表示する |
| 全経路失敗 | 候補0件と区別して外部サービス障害を表示する |
| Apple Maps起動失敗 | 目的地座標のコピーを提示する |

### 5. MVPスコープと責任境界（RD-03）

#### 5.1 MVP必須

- 初回説明、位置権限要求、提案条件入力、2回目以降の前回条件再利用・変更。
- 候補を1件ずつ見せるカード型提案、詳細、候補ピン、概要ルート、推薦理由、予測所要時間、鮮度表示。
- `興味あり / 興味なし / 行ったことがある / ここに行く` の操作と、興味ありスポットを後から確認できる一覧。
- Apple Mapsへの目的地引き渡し。
- 同意したβユーザーの匿名イベント計測。
- 候補0件、権限拒否、タイムアウト、部分障害、外部ナビ失敗への対応。
- 走行中の操作を促さない注意表示。
- WeatherKitによる、天候依存属性を持つSpotの詳細表示時の天気注意情報。天気は推薦計算および候補除外に使用しない。

#### 5.2 MVP対象外

- アカウント、複数端末同期、任意出発地点、帰着時刻指定、車両・排気量プロフィール。
- アプリ内ターンバイターンナビ、走行追跡、走行完了判定、オフライン地図。
- リアルタイム渋滞最適化、リアルタイム道路規制のアプリ内統合。
- 給油・食事を含む旅程、複数日、予約。
- Android、iPad最適化、CarPlay / Android Auto。
- UGC、SNS、通知、ML / LLM推薦。
- Google Places由来コンテンツの表示・Canonical DBへの保存。

#### 5.3 MVPと将来版の境界

| 領域 | MVP | 将来版 |
|---|---|---|
| 提案 | ルールベース、最大5件を1件ずつ表示 | ML / LLMによる高度な個人化、提案件数・探索方式の最適化 |
| 嗜好 | 匿名installation単位の興味あり・興味なし・訪問済み | アカウント同期、複数端末、長期嗜好モデル |
| 地域 | 九州7県 | 日本全国、複数日・広域旅程 |
| ナビ | Apple Mapsへ目的地を引き渡す | 内蔵ナビ、CarPlay、走行追跡 |
| データ | 公開Web情報を候補発見に使い、継続収集・月次更新する | UGC、提携データ |
| クライアント | iPhone / iOS 17以上 | Android、iPad最適化 |

固定件数の収集完了をMVPの目的にせず、九州7県を継続的に収集・更新できることをMVPのデータ基盤要件とする。

#### 5.4 責任境界

```text
アプリ
  現在地取得 → 条件設定・再利用 → 1件ずつ提案 → リアクション／詳細 → 目的地引き渡し

Apple Maps
  最新ルート選択 → 走行案内 → 走行中の経路変更 → 到着
```

- 所要時間と帰着予想は予測であり保証しない。
- 交通規制、天候、現地標識は最新情報を優先する。
- Apple Maps起動後の走行・帰着は追跡しない。

### 7. UXフローと画面要件（RD-05）

RD-05は一覧型UXを否認し、プロダクトコンセプトである「検索ではなく提案」を主動線にするため再設計する。本節は再レビュー用の更新案であり、低忠実度モックとユーザビリティ確認をもって確定する。

#### 7.1 初回起動フロー

```text
初回説明
  ↓
提案条件設定
  ├─ 位置権限拒否 → 理由説明・設定導線
  └─ 現在地取得
       ↓
時間 → 興味 → 高速可否 → 提案を受ける
       ↓
提案カード（1件） ── 0件／障害 → 条件変更・再試行
  ├─ 興味なし／行ったことがある → 記録 → 次の提案
  ├─ 興味あり → 保存 → 次の提案または興味あり一覧
  └─ 詳細
       ↓
提案詳細 → ここに行く → 安全確認 → Apple Maps
```

#### 7.2 2回目以降の起動フロー

```text
ホーム
  ├─ 前回条件で提案を受ける → 現在地を再取得 → 提案カード
  ├─ 条件を変更する → 提案条件設定 → 提案カード
  └─ 興味ありを見る → 興味あり一覧 → 詳細 → 安全確認 → Apple Maps
```

- 初回説明と包括的なオンボーディングは初回だけ表示する。安全上・利用条件上の重要変更がある場合は再表示できる。
- 前回の時間、興味、高速可否を端末に保存し、2回目以降は再利用を選べる。正確な現在地は保存せず、提案開始時に毎回取得する。
- 前回条件を無断で即実行せず、「前回条件で提案を受ける」と「条件を変更する」を明示する。

#### 7.3 リアクションと提案継続

- `興味あり`: installation単位で保存し、興味あり一覧から後で確認・解除できる。記録後は次の提案へ進める。
- `興味なし`: installation単位で保存し、解除されるまで今後の推薦から基本的に除外する。候補不足時も自動復活させず、設定画面から履歴を解除できるようにする。
- `行ったことがある`: installation単位の訪問済み情報として保存する。推薦では除外を既定とし、将来の「再訪も含める」設定に備えて状態を保持する。
- リアクション未選択でも詳細を開ける。戻った場合は同じカードへ復帰する。
- 最大5件を使い切った場合は、興味あり一覧、条件変更、同条件で再提案の導線を示す。同じセッションで同一Spotを再表示しない。
- アカウントは作らず、別端末への同期およびアプリ削除後の復元はMVP対象外とする。

#### 7.4 画面一覧

| ID | 画面 | 必須要素 |
|---|---|---|
| S01 | 初回説明 | 提案内容、時間は予測、安全上の注意、開始ボタン |
| S02 | ホーム／提案開始 | 前回条件の要約、前回条件で提案、条件変更、興味あり一覧 |
| S03 | 提案条件 | 現在地状態、時間、興味、高速可否、提案開始ボタン |
| S04 | 提案カード | 1件の名前、特徴、合計時間、帰着予想、理由、営業等の警告、鮮度、3リアクション、詳細 |
| S05 | 提案詳細 | 概要、MapKit、概要ルート、時間内訳、営業時間、出典・鮮度、天候依存時の天気注意ポップアップ、ここに行く |

#### 7.5 低忠実度モック

```text
┌─────────────────────────┐
│ 提案条件を決める        │
│ 現在地  [取得済み]      │
│ 時間    [2h][4h][半日]  │
│ 興味    [海][景色][Cafe]│
│ 高速    [使わない  ○]   │
│ [この条件で提案を受ける]│
└─────────────────────────┘

┌─────────────────────────┐
│ 糸島・桜井二見ヶ浦      │
│ 往復・滞在 1時間55分    │
│ 16:05帰着予想 / 海・景色│
│ 理由: 時間内・興味一致  │
│ 営業情報を要確認        │
│ [興味あり] [興味なし]   │
│ [行ったことがある]      │
│ [詳細を見る]            │
└─────────────────────────┘
```

#### 7.6 UI受入条件

- 初回はS01からS07まで、2回目以降はS02からS07まで片手操作とVoiceOverで主要操作へ到達できる。
- Dynamic Typeで本文を拡大しても主要CTAが失われない。
- 色だけで選択、警告、エラーを伝えない。
- 候補カードの時間は `往復 + 滞在 + 帰着余裕` を明示する。
- ローディング中の重複送信を防ぐ。
- エラーは技術語を避け、原因区分、再試行可否、次の操作を示す。
- スワイプ操作を必須にせず、すべてボタンでも完了できる。
- 走行中利用を前提とせず、Apple Maps移行後に本アプリの操作を促さない。
- カードは常に1件を主表示し、一覧比較を主動線にしない。
- 各リアクション後に保存結果と次の遷移が分かり、誤操作を取り消せる。
- 初回説明済み・前回条件・各リアクションが再起動後もinstallation単位で維持される。

### 8. 推薦・時間計算（RD-06）

#### 8.1 時間定義

```text
estimated_total_minutes
  = outbound_minutes
  + stay_minutes
  + return_minutes
  + return_buffer_minutes
```

- `return_buffer_minutes` は `max(15分, ceil((往路 + 復路) × 10% / 5分) × 5分)`。
- ハード条件は `estimated_total_minutes <= available_minutes`。
- 往路・復路は個別に計算し、同一時間と仮定しない。
- 営業時間が「閉店」と確定する候補は除外する。営業時間不明は警告して残す。
- 経路を取得できない候補は除外する。
- 天気は推薦計算、ランキング、候補除外に使用しない。

#### 8.2 候補抽出

1. 現在地から片道180分以内のCanonical Spotを位置検索する。
2. 経路と所要時間を取得する。
3. 時間、営業状態、経路取得可否でハードフィルタする。
4. 端末から受け取った `興味なし` と `行ったことがある` のSpot IDを除外する。
5. 下記スコアを計算し、決定論的に並べる。
6. 暫定カテゴリ・特徴が偏りすぎないよう多様性を調整する。
7. 上位5件を返し、クライアントが1件ずつカード表示する。

#### 8.3 スコア v1

| 要素 | 点数 | 規則 |
|---|---:|---|
| 興味一致 | 0〜40 | 選択タグとの一致率。`any` は20点固定 |
| 時間適合 | 0〜25 | 利用可能時間を有効活用しつつ余裕を残す候補を優先 |
| 未訪問 | 0または15 | 訪問済み除外を適用しない回帰・将来設定では、`visited` がなければ15点 |
| データ信頼度 | 0〜10 | 必須属性のconfidence平均 |
| 編集人気度 | 0〜10 | β用の手動優先度。根拠を管理する |
- `not_interested` は同一セッションだけでなく今後の推薦から基本的に除外し、利用者が履歴を解除した場合だけ再び対象にする。
- `visited` は訪問済みとして保持し、MVPでは推薦から除外する。
- 同点は `score desc → estimated_total_minutes asc → spot_id asc` で固定する。
- 推薦理由は上位寄与要素から最大3件生成する。

#### 8.4 固定回帰ケース

- 2時間・海・高速なし: 時間内の海候補が優先される。
- 4時間・山・高速可: 山候補が入り、閉店確定Spotは出ない。
- 1時間・温泉: 条件該当がなければ空配列を返す。
- 訪問済みと未訪問が同条件: 未訪問が上位になる。
- 1件だけ経路障害: 残候補と `PARTIAL_ROUTE_FAILURE` を返す。
- 全件経路障害: 503を返し、候補0件扱いにしない。
- 同一入力・同一データ版: 同順位を返す。

### 9. API契約（RD-06）

機械可読な個別契約の正本は [mvp-openapi-v1.yaml](mvp-openapi-v1.yaml) とする。RD-05再設計に伴い、除外・訪問済み入力などの契約更新が完了するまでAPI v1は再レビュー中として扱う。

#### 9.1 MVP全体のAPI構成

```text
iOS
  ├─ 提案開始 ─────────────→ Recommendation API
  │                            ├─ Spot Query
  │                            ├─ Travel Time Estimation
  │                            └─ Recommendation Rule
  ├─ カードへの反応 ────────→ 端末内の嗜好状態を更新
  │   └─ 分析同意済みの場合 → Interaction API
  └─ データ削除 ────────────→ Privacy API

Data Worker（非公開・管理系）
  └─ 発見 → 取得 → 検証 → 名寄せ → 公開 → 月次再確認
```

- 公開APIはRecommendation、Interaction、Privacyの3領域に限定する。
- Spot Query、移動時間推定、推薦ルールはRecommendation API内部の責務であり、iOSから個別に呼び出さない。
- Data Workerは一般公開APIではない。収集元の資格情報と管理操作をiOSへ公開しない。
- 興味あり・興味なし・訪問済みはMVP機能に必要な端末内状態として、分析同意の有無にかかわらず保持できる。サーバへの分析イベント送信は明示同意済みの場合だけ行う。

#### 9.2 API一覧と責務

| API | エンドポイント | 目的 | 主な呼出元 |
|---|---|---|---|
| Recommendation | `POST /v1/recommendations` | 条件、現在地、除外Spot、訪問済みSpotから最大5件を生成する | S03 提案開始、再提案 |
| Interaction | `POST /v1/interactions` | 同意済みの匿名表示・リアクション・選択イベントを最大50件送る | S04〜S07、バックグラウンド再送 |
| Privacy | `DELETE /v1/installations/{installation_id}/data` | サーバ上の匿名行動データ削除を要求する | S08 設定・プライバシー |

興味あり一覧は端末に保存したSpotスナップショットを表示し、MVPでは専用サーバAPIを設けない。再提案時に最新候補情報を受け取った場合は同じ `spot_id` の表示内容を更新する。アカウント同期やサーバ側お気に入りAPIは将来版とする。

#### 9.3 画面フローとの対応

| 画面・操作 | API | 成功時 | 失敗時 |
|---|---|---|---|
| S03「提案を受ける」 | Recommendation | S04で先頭カードを表示 | 0件、部分障害、全障害を区別して表示 |
| S04リアクション | Interaction（同意時のみ） | 端末保存を確定し次カードへ | 端末保存は維持し、イベントを後で再送 |
| S05「ここに行く」 | Interaction（同意時のみ） | S07へ進む | 計測失敗でナビ導線を止めない |
| S07 Apple Maps起動 | Interaction（同意時のみ） | `route_started` を記録 | 座標コピーを提示し、計測は状態に応じて再送 |
| S08匿名データ削除 | Privacy | 完了を表示し端末の未送信分析イベントも削除 | 再試行と問い合わせ導線を表示 |

#### 9.4 共通契約

- HTTPSのみ、JSONはUTF-8。
- エラーは `application/problem+json` とし、機械判定用 `code` と `request_id` を返す。
- 推薦のサーバ処理期限は4秒、iOSクライアントのタイムアウトは5秒。
- イベントはクライアント生成UUIDの `event_id` で冪等にする。
- 候補0件は200と空配列、依存障害は503または504で区別する。
- 503、504、通信断だけ再試行対象とし、指数バックオフで最大1回自動再試行する。
- APIレスポンスに秘密情報、内部例外、正確なDB識別子を含めない。

#### 10.1 対象範囲と段階

| 段階 | 地域 | 件数の扱い | 目的・完了条件 |

| 初期テスト | 福岡市および周辺の日帰り圏 | 100件程度 | Data Contract、欠損率、名寄せ、推薦、月次更新の一連の処理を実データで検証する |

- 初期テストの福岡100件程度は、MVP公開地域を福岡に限定する意味ではない。
- 公開時の件数達成だけを目的にせず、県別・情報源別の取りこぼしと品質を測定して収集を反復できることを優先する。
- 九州7県での最低カバレッジ指標は、実データ調査後に「県別公開Spot数、主要な興味の充足率、更新成功率、手動レビュー滞留」の組合せで定める。

#### 10.2 分類方針

- 1スポットに複数カテゴリと複数タグを付与できる多対多構造とする。単一の主カテゴリは必須にしない。
- カテゴリ・タグの正式な分類体系は先に固定せず、初期テストで収集した実データを分析した後に確定する。
- 画面入力に使う興味コードと、データ分類用のカテゴリ・タグを分離し、対応表にバージョンを持たせる。
- 分類確定前は、収集元の分類語、説明文、特徴、立地、周辺道路などの原情報を失わず保存し、暫定ラベルを付けても原情報を上書きしない。
- `winding` など解釈を伴う特徴は、出典の記述または検証可能な算出根拠を保存する。

分類体系の確定手順は次のとおりとする。

```text
実データ収集 → 分類語・特徴の抽出 → 重複・粒度分析
→ カテゴリ／タグ案作成 → 推薦・UXで検証 → taxonomy v1承認
```

#### 10.3 収集時の必須情報

- 収集レコードID、名称、緯度経度または位置を特定できる住所。
- 原文の説明または規約上保存可能な要約、収集元が示す分類語、特徴・補足情報。
- 出典URL、情報源種別、原典ID、取得日時、確認日時、利用条件・ライセンス判定。
- 営業時間、営業・閉業状態、駐車場、二輪可否、通行可否、滞在目安は取得できる範囲で保存し、不明を虚偽の値で埋めない。
- 変動情報は値だけでなく、確認元、確認日時、確認方法、信頼度を属性単位で保持する。
- 画像は権利と配信方法を確認できるものだけ使用する。確認できるまでプレースホルダーを使う。

候補発見時に本文の保存が許可されない情報源については、URL、短い事実メモ、抽出特徴だけを保存し、公開説明文は利用可能な別ソースまたは独自記述から作成する。

#### 10.4 ソース方針と信頼性

スポット候補の発見は公式サイトに限定せず、検索結果、観光記事、施設紹介、地図・オープンデータなど、Web上で公開された幅広い情報源を利用できる。ただし、閲覧可能であることと再利用・保存可能であることは同一ではないため、利用規約、著作権、robots、API条件を情報源ごとに確認する。

| ソース | 主な役割 | Canonicalへの利用条件 |
|---|---|---|
| OSM Data | 座標、道路、基本属性、候補発見 | ODbLと帰属条件を満たす |
| 自治体・観光協会・施設公式情報 | 正式名称、営業・閉業、営業時間、駐車場、通行案内 | 各利用条件を確認し、変動情報の優先確認先とする |
| その他の公開Web情報 | 候補発見、特徴・評判の手掛かり | 原則として発見用途。保存・転載可能な事実だけを規約に従って利用する |
| 手動確認 | 自動確認不能、矛盾、誤り訂正、現地性の高い情報 | 確認者、根拠、日時を保存する |
| Google Places | MVP不採用 | Place IDを含めCanonicalに取り込まない |

- 営業時間、閉業、休業、駐車場、二輪可否、通行可否など時間で変化する情報は、施設・道路管理者・自治体等の信頼できる情報源で確認する。
- 情報源が競合する場合は、更新日時と属性ごとの信頼度を比較し、自動解決できなければ人間レビューへ送る。
- OSMの標準タイルサーバはバルクデータ取得元として使わず、地図表示にはMapKitを使う。[OpenStreetMap Copyright](https://www.openstreetmap.org/copyright)、[OSM Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/)
- Google PlacesはMapKit中心のMVPでは混在させず不採用とする。[Google Places policies](https://developers.google.com/maps/documentation/places/web-service/policies)

→ 月次再取得・差分検出 → 自動反映または人間レビュー

### 11. Spot・Source・Freshness・行動スキーマ（RD-08）

#### 11.1 論理エンティティ

| エンティティ | 主な役割 |
|---|---|
| `spots` | 公開するCanonical Spot。UUIDとPostGIS位置を持つ |
| `spot_candidates` | 幅広い情報源から発見した公開前候補と処理状態 |
| `spot_sources` | 原典ごとの値・説明・分類語・特徴、原典ID、URL、ライセンス、取得・確認日時 |
| `spot_field_sources` | Canonicalの各属性がどのSourceを正本にしたか追跡する |
| `categories` / `spot_categories` | 複数カテゴリとSpotの多対多関係。taxonomy版を持つ |
| `tags` / `spot_tags` | 複数タグとSpotの多対多関係。taxonomy版を持つ |
| `spot_hours` | 曜日・例外日・不明状態を表現する営業時間 |
| `data_review_tasks` | 自動確認不能・矛盾・低信頼・名寄せ曖昧の人間レビューキュー |
| `installations` | 匿名installation ID、同意状態、削除トークンハッシュ、将来のアカウント紐付け状態 |
| `users` | 将来のアカウント主体。MVPではレコードを作成せず、導入時に有効化する |
| `user_installations` | 将来、1つのuser IDと複数installation IDを紐付ける中間関係。MVPでは未使用 |
| `interaction_events` | 分析同意済みの匿名installation IDに紐づく行動イベント |
| `data_deletion_requests` | 削除要求の受付・完了監査。削除対象本文は保持しない |

`spots` はアプリが利用する正式なCanonical Spot、`spot_sources` はWeb、OSM、公式サイト、手動確認等から得た元データであり、同一エンティティとして扱わない。Canonicalの各属性は `spot_field_sources` を介して採用Source、採用時刻、採用理由、採用者またはルール版を追跡できることを必須とする。

`spot_sources` は少なくとも `source_type`、`source_record_id`、`source_url`、`retrieved_at`、`verified_at`、`verification_status`、`license_status`、`confidence` を保持する。`source_type` は `official_web / general_web / osm / public_open_data / manual_verification / other` を表現でき、一般Webサイトを公式サイトとは別種別で登録できることを必須とする。

#### 11.2 主要制約

- IDはUUID、位置は `GEOGRAPHY(Point, 4326)`。
- 緯度経度はDB位置型を正とし、別カラムへ二重管理しない。
- Canonical Spotと複数Sourceを分離する。
- Spotに複数カテゴリを付与でき、単一主カテゴリを必須にしない。
- Source採用は固定の全体順位で決めず、属性ごとに「当該属性への権威性、確認状態、取得・確認日時、複数Source一致、抽出確度、利用条件」を評価する。同じSourceでも、名称、座標、営業時間、駐車場情報で採否が異なってよい。
- 一般Webから収集できることとCanonicalへ採用できることを分離する。利用条件または根拠を確認できない値はSourceとして保持できるが、Canonicalの採用値にはしない。
- 複数Sourceが矛盾し、属性別ルールで一意に決定できない場合は既存Canonical値を自動上書きせず、対象属性単位のレビューへ送る。
- 100m以内かつ正規化名称類似度0.8以上を重複候補とする。自動統合せず手動承認する。
- `source_type + source_record_id` は一意。
- `interaction_events.event_id` は一意で再送を重複計上しない。
- MVPの行動・同意・削除対象データはuser IDではなくinstallation IDへ紐付ける。各テーブルへ将来のuser IDを直接混在させず、`user_installations` を介して既存installation IDをアカウントへ関連付けられる構造にする。
- 将来のアカウント導入時に、既存履歴を引き継ぐか、紐付けをいつ実行するか、複数端末の競合をどう解決するかは未決定とし、移行ADRで定める。

#### 11.3 月次チェックとFreshness

- チェック周期とFreshness期限を別概念として管理する。全Canonical Spotおよび有効な全Sourceを月1回チェック対象へ登録し、最終試行日時、成功日時、結果、次回予定日時を記録する。
- 月次チェックでは可能な限りAIまたは自動スクリプトで再取得・差分検出・無変更確認を行う。自動取得不能、矛盾、重大差分、低信頼、利用条件不明は属性単位の手動レビュー対象とする。
- 一時的な更新失敗では直ちにCanonical値を削除しない。失敗理由と再試行予定を記録し、Freshness期限内は直近の確認済み値を維持する。期限超過後は下表の処理を適用し、安全・営業に関する重大疑義は確認まで非公開にする。
- 天気と経路などリアルタイム系データはSource月次更新の対象外とし、リクエスト時または専用周期で管理する。

| 属性 | Freshness期限 | 期限超過時 |
|---|---:|---|
| 名称 | 180日 | staleとしてレビュー対象。確認済み旧値は直ちに削除しない |
| 座標 | 365日 | staleとしてレビュー対象。重大な位置疑義は公開停止 |
| 分類 | 180日 | stale表示、重大差分は人間レビュー |
| 営業時間 | 30日 | `unknown` として警告 |
| 駐車場・二輪可否 | 90日 | 不明表示 |
| 営業・閉業・通行可否 | 30日または短い個別期限 | 重大な疑義は確認まで非公開 |
| 移動時間Providerの参照データ | Provider仕様に従う | stale判定が可能な場合は警告し、取得不能時は候補除外または明示的エラー |
| 天気 | 60分 | 再取得、失敗時は利用不可表示 |
| 経路 | リクエストごと | キャッシュする場合も最大15分 |

#### 11.4 行動イベント

```text
shown / interested / not_interested / visited / selected / route_started
```

- `event_id`、匿名installation ID、session ID、recommendation ID、spot ID、時刻、順位、時間選択、興味コードを保持する。
- 正確な現在地、走行軌跡、Apple Maps内の行動はイベントへ含めない。
- `shown` は画面に実際に表示された候補だけ記録する。
- `interested / not_interested / visited` の機能状態は端末内に保持し、分析イベントとは分離する。
- 本節は暫定仕様であり、RD-05のカード表示、興味あり、興味なし、行ったことがある、興味あり一覧のUX修正完了後に、イベント名・発火条件・重複計上ルールを再レビューして確定する。

### 12. 推薦用の移動時間推定と外部Map連携（RD-09）

#### 12.1 責任境界と決定事項

- Bike EasyFinderの役割は、利用可能時間と興味に合うツーリング先の提案とする。
- アプリ内ではルート検索、ルート形状の生成、ターンバイターンナビゲーションを行わない。
- 推薦判定のため、現在地からSpotまでの距離と所要時間を取得する。
- Spot選択後は目的地情報をApple MapsまたはGoogle Mapsへ渡し、実際のルート検索・ナビゲーションを外部Mapアプリへ委譲する。
- Valhallaと独自ルーティングはMVP対象外とする。独自ルート、ワインディング優先、海沿い優先、市街地回避などが必要になった場合だけ、MVP後に再評価する。

#### 12.2 移動時間取得方式の選定

Apple MapKit、Google Routes API、その他APIを比較し、次を確認して採用方式を決める。

- 九州7県における距離・所要時間の取得可否と精度。
- 料金、無料枠、レート制限、キャッシュ・保存・表示に関するAPI制約と利用規約。
- iOS／SwiftUI／MapKitとの親和性、バックエンド経由の要否、APIキー保護方法。
- 推薦APIの応答時間、タイムアウト、部分障害時のフォールバック。
- 推薦時の推定値と外部Mapアプリが提示する値の差。許容差はProvider選定時に固定する。

#### 12.3 外部Map連携仕様

- 最低限、目的地座標とSpot名称を渡す。
- 出発地は現在地を基本とし、外部Map側で最新位置を利用できる連携方式を優先する。
- 経由地はMVPでは必須とせず、必要性が確認された場合のみ追加する。
- Apple Mapsを標準導線とし、Google Mapsが利用可能な場合に選択肢として提示する案を基本設計で確定する。
- Google Mapsが未インストールの場合もApple MapsまたはWebへの安全なフォールバックを提供する。
- 外部Mapへ遷移後のルート、ETA、交通情報、ナビゲーション品質は各Mapアプリの責任範囲とする。

#### 12.4 九州7県POCと合格基準

- 福岡限定ではなく九州7県すべてを対象とする。
- 各県で最低1件以上を実機確認し、全体として都市部、山間部、海沿い、高速利用など異なる条件を含める。県別件数と総件数はProvider候補確定後に固定する。
- 九州7県の現在地から、利用可能時間を考慮した候補を返せる。
- 推薦用の距離・所要時間を取得でき、実利用で致命的な待ち時間がない。
- Apple MapsおよびGoogle Mapsの対象導線を正常起動でき、選択したSpotへ遷移できる。
- 推定値と外部Map結果の差が、承認済みの許容範囲に収まる割合を計測できる。
- Provider障害時に、候補除外、再試行、または明示的エラーの承認済み動作となる。
- 費用と利用制約がRD-12の運用条件内に収まる。

### 13. 天気・道路情報・安全（RD-10）

#### 13.1 天気

- WeatherKitをMVPで採用し、天候依存属性を持つSpotの詳細を開いた時だけ、候補地点の現在から訪問想定時間帯までの予報を取得する。
- Apple Developer Programに含まれる月50万call枠内で運用し、超過課金は行わない。
- Apple Weatherの帰属表示と法的リンクを表示する。
- 天気は推薦ランキングの加点・減点、ハードフィルタ、候補除外に使用しない。雨・風・気温などを理由にSpotを自動除外しない。
- 取得した予報とSpotの天候依存属性を照合し、注意が必要な場合は詳細画面にポップアップを表示する。行くかどうかの最終判断は利用者に委ねる。
- WeatherKit取得失敗時も推薦と詳細表示を継続する。詳細画面の案内文言は基本設計で確定する。

WeatherKitはiOS 16以上で利用でき、Apple Developer Program会員には月50万callが含まれる。[Apple WeatherKit](https://developer.apple.com/weatherkit/)

天候依存属性は複数値を保持できる列挙型として設計し、MVPでは少なくとも `sunny_recommended`（晴れ向き）を定義する。将来、互換性を保って次の値を追加できる形式とする。

- `all_weather`（雨でも可）
- `rain_not_recommended`（雨天非推奨）

属性の手動付与／収集時AI判定、単一／複数段階の判定方式、雨・曇り・降水確率・風・気温等のポップアップ発火条件は未確定とし、別途決定する。属性値には判定根拠と採用Sourceを追跡できるようにする。

#### 13.2 道路情報

- リアルタイム道路規制はMVPおよび将来版のアプリ側対象外とし、JARTIC統合を実装候補に含めない。
- Bike EasyFinderは道路状況、通行可否、実際の走行ルートを保証しない。
- 道路規制と実際のルート判断はApple Maps／Google Mapsおよび現地標識へ委譲する。

#### 13.3 安全表示

- ユーザー画面に「最終確認時刻」は表示しない。Sourceと属性ごとのFreshnessは内部で継続管理し、必要性が生じた場合に表示追加を再検討する。
- S07の外部Map遷移前に「走行中に操作しない」「道路状況・通行可否・ルートを保証しない」「現地標識と外部Mapを優先する」を表示する。
- 詳細画面で発火中の天気注意をS07にも簡潔に再表示するかは、RD-05の画面設計で決定する。
- 重大警告を色だけで表現しない。
- 安全免責への同意だけで機能上の安全措置を代替しない。

### 14. プライバシー・分析・アカウント（RD-11）

#### 14.1 方針

- MVPではアカウントを作成せず、匿名installation IDでユーザーを識別する。
- 課金、Web版、複数端末同期、履歴引き継ぎを実装する段階でuser IDを導入できる設計とする。
- 位置権限は `When In Use` のみ。
- 正確な現在地はアプリ利用時に取得し、推薦処理だけに使用する。永続保存せず、生GPS軌跡、バックグラウンド位置、自宅・勤務先推定も保存しない。
- 利用分析は全ユーザーを基本対象とする。ただし初回に収集目的を明示して同意を取得し、同意しないユーザーまたは撤回したユーザーの分析データは収集しない。拒否・撤回しても推薦機能を利用できる。
- 広告、第三者広告SDK、クロスアプリトラッキングには使用せず、自社サービス改善用の分析としてATTが不要な範囲に限定する。
- 前回条件、興味あり、興味なし、訪問済みは製品機能の端末内状態として保持し、分析同意とは分離する。

#### 14.2 データ一覧

| データ | 利用目的 | 保存場所 | 保持期間 | 削除条件 | 第三者送信 |
|---|---|---|---|---|---|
| 正確な現在地 | 推薦・移動時間推定 | 処理中メモリのみ | 推薦処理完了まで | 処理完了または失敗時に破棄 | 自社API、採用する移動時間Provider |
| Spot座標 | 地図・天気・外部ナビ | 端末・DB | 棚卸し後に決定 | Spot非公開化・Source削除規則に従う | Apple MapKit、WeatherKit、Apple Maps |
| 前回条件・Spotリアクション | 提案再開、保存、除外、訪問済み管理 | 端末のみ | 棚卸し後に決定 | 利用者による消去またはアプリ削除 | 推薦時に対象Spot IDのみ自社APIへ送信 |
| 匿名installation ID・同意記録 | 同意管理、KPI、匿名データ削除、将来のアカウント紐付け | 端末・DB | 棚卸し後に決定 | 匿名データ削除要求または個別の失効条件 | なし |
| 行動イベント | MVP検証、自社サービス改善 | DB | RD-05確定後のイベント定義と棚卸し後に決定 | 同意撤回・匿名データ削除要求・保持期限到来 | なし |
| 集計KPI | 継続判断、サービス改善 | DBまたは分析ファイル | 棚卸し後に決定 | 個人・端末へ戻せる集計は削除対象。不可逆集計の扱いはPrivacy Policyに記載 | なし |
| 運用ログ | 障害・不正対策 | サーバログ | 棚卸し後に決定 | 保持期限到来。installation IDを含む場合は削除要求の対象範囲を別途定義 | 採用監視事業者は基本設計で申告 |

保持期間を一律に定めず、保存対象となる全データを棚卸ししたうえで、各データの利用目的、保存場所、保持期間、削除条件、第三者送信有無を個別に確定する。ログにはリクエスト本文、緯度経度、削除トークンを記録しない。

#### 14.3 匿名ID・同意・削除

- 初回にランダムなinstallation IDと削除トークンを生成する。
- 初回起動時に、分析対象データ、利用目的、第三者送信、保持・削除の考え方を示し、分析同意を取得する。分析同意前は行動イベントを収集・送信しない。
- 同意日時、Privacy Policy版、同意状態を端末へ保存し、設定画面からいつでも同意を撤回できるようにする。
- 同意撤回後は新規イベントの収集・送信を停止し、未送信イベントを削除する。既送信データを削除するか保持期限まで保持するかは、同意画面とPrivacy Policyで明示し、匿名データ削除機能とは別に扱う。
- MVPでS08から匿名ユーザーデータ削除要求を送信できるようにし、installation IDに紐づく生データを削除する。
- 削除要求は現行の削除トークン方式を採用し、サーバにはトークンのハッシュだけを保存する。
- 集計済みで個人・端末へ戻せない統計は削除対象外とし、Privacy Policyに記載する。
- アプリ削除・再インストール等で削除トークンを失った場合の救済策はMVP後に再検討する。

#### 14.4 将来拡張と未決事項

- 将来のアカウント導入時に既存installation IDの履歴を新規アカウントへ引き継ぐか、どのタイミングで紐付けるかは未決定。
- 課金方式は未確定。Apple In-App Purchase、サブスクリプション、Web課金の選択により、アカウント要件を再評価する。
- Web版、複数端末同期、履歴引き継ぎはMVP後のスコープとする。
- 行動イベントの具体的な定義はRD-05の変更に依存するため、RD-05確定後に一覧、発火条件、重複計上ルールを再整理する。
- 各データの具体的な保持期間は、全データ棚卸し後に個別判断する。

#### 14.5 App Store申告

- App Store Connectでは、実装完了時点の位置情報、識別子、製品操作、診断情報と第三者送信を再棚卸しし、実装と一致する内容を申告する。
- 端末だけで処理されサーバへ送られない情報と、サーバへ送る情報を区別する。
- Privacy Policyの公開URLをTestFlight外部テスト前に用意する。
- Appleは位置情報の目的説明と同意、App Storeでのプライバシー情報を求めている。[App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/)

### 15. システム境界と環境（RD-12）

#### 15.1 論理構成

```text
iOS / SwiftUI
  ├─ MapKit / CoreLocation
  ├─ WeatherKit
  ├─ Apple Maps
  └─ HTTPS
       ↓
FastAPI モジュラーモノリス
  ├─ Recommendation
  ├─ Spot Query
  ├─ Interaction / Privacy
  └─ Worker
       ├─ PostgreSQL + PostGIS
       ├─ 移動時間Provider（RD-09で選定）
       └─ 九州7県の公開Web・OSM・公共／公式データ取込
```

iOSは選択したSpotをApple MapsまたはGoogle Mapsへ渡し、ルート検索とナビを外部委譲する。MVP構成にValhallaおよび独自ルーティング基盤は含めない。

#### 15.2 環境

- `local`: 固定JSON、ローカルDB、モック外部サービス。
- `staging`: TestFlight、匿名化した実データ、実WeatherKit、移動時間Providerの検証環境。
- `production`: Ver0.1提供用。stagingと同じアーキテクチャおよびデプロイ構成を使用し、スペック差は許容する。
- stagingとproductionのドメイン、DB、シークレット、APIエンドポイント、スペック、ログ保持、外部サービス設定を分離し、差分を「環境差分一覧」として管理する。
- 環境差分一覧は構成変更時に更新し、意図しない構成差を作らない。production反映前にstagingで同一変更を確認する。
- 個人データを本番からlocalへコピーしない。
- インフラ事業者とリージョンは基本設計ADRで決める。PostGIS、暗号化、日次バックアップ、月額上限を必須選定条件とする。

#### 15.3 認証・不正対策

- ユーザー認証は行わない。
- 推薦APIはレート制限を行い、installation IDを認証資格として扱わない。
- 削除要求は端末だけが保持する削除トークンで保護し、サーバにはハッシュを保存する。
- 管理・取込機能は公開APIと分離し、管理者認証を必須にする。
- シークレットをアプリ、リポジトリ、ログへ保存しない。

### 16. 非機能要件（RD-12）

#### 16.1 性能・可用性

- 推薦API p95 5秒以内を暫定目標とし、初回候補表示はユーザー操作から3秒程度を目標とする。
- 候補表示成功率95%以上。
- β期間の月間可用性目標99.0%。計画停止は事前通知し集計から分離する。
- 外部サービス部分障害時は、取得済みの安全な候補だけ返すか明示的に失敗する。
- 性能目標は実測データ蓄積後に再評価する。ユーザー増加時はCPU、メモリ、DB負荷、API応答時間を確認し、必要な場合だけスケールまたはチューニングする。

#### 16.2 セキュリティ・ログ

- TLS 1.2以上、DBとバックアップの保存時暗号化。
- 最小権限、環境ごとの秘密情報分離、依存関係脆弱性検査。
- 構造化ログにrequest ID、処理時間、結果件数、エラーコードを記録する。
- 緯度経度、削除トークン、WeatherKit認証情報、リクエスト本文をログへ残さない。
- Severity 1・2障害はβを停止し、再開条件を記録する。

#### 16.3 バックアップ・復旧

- PostgreSQLを日次バックアップし、7世代以上保持する。
- 月1回、stagingへリストア試験を行う。
- 目標RPO 24時間、RTO 8時間。
- バックアップ対象には少なくともCanonical Spot、Source情報、手動補正済みデータ、taxonomy・設定値、ユーザー推薦状態、Privacy同意情報、削除管理情報、重要な運用設定を含める。
- 端末だけに保存するユーザー推薦状態はサーババックアップ対象外であることを明示し、端末バックアップからの復元可否と消失時の動作を定義する。将来サーバ保存へ変更した場合はバックアップ対象へ追加する。
- 各対象を「必ず復旧するデータ」と「原典から再収集・再生成できるデータ」に分類し、復旧優先度と手順を基本設計で定める。
- OSM・公共データ等、再収集可能なデータは取込元、取得版、手動補正との差分を追跡し、再生成可能にする。

#### 16.4 監視

- CPU、メモリ、DB負荷、APIレスポンスタイム、エラー率、外部API・インフラ費用を最低限の監視対象とする。
- 閾値、通知先、一次対応、エスカレーション条件は基本設計で定める。
- 費用アラートは月額上限に対する使用率で通知し、意図しない自動スケールや外部API利用増を検知できるようにする。

#### 16.5 アクセシビリティ・互換性

- iOS 17以上の現行・一世代前のiPhone画面サイズで確認する。
- VoiceOver、Dynamic Type、コントラスト、44pt以上の主要タップ領域を確認する。
- 正確な位置情報を無効にした端末では取得精度不足を説明し、推薦不能なら再試行を促す。

### 17. 費用・実装計画（RD-12）

#### 17.1 月額上限と費用最小化

- MVPの外部API・インフラ合計を月額10,000円以内とする。上限を超える構成変更は事前に再承認する。
- Apple Developer Program、開発端末、ドメイン費用は上限外として実費管理する。
- WeatherKitは月50万callの会員枠を超えない。自動的な有料プラン移行を行わない。
- 予算の70%で警告、90%で新規収集・非必須処理を抑制、100%で原因を確認するまで拡大を止める。
- 移動時間Providerの採用・切替で月額上限を超える場合は、上限を再承認する。
- MVPには課金収益がないため、常時高スペック構成を避け、不要なマネージドサービスを増やさず、使用量と実測負荷に応じて後から拡張する。
