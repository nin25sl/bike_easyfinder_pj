# バイク目的地提案アプリ MVP 要件定義書 v1

> **目的とゴールの違い**
>
> - **目的** = Why（なぜこのMVPを実施するか）
> - **ゴール** = Done 条件（何を満たせば要件定義完了とするか）

## 目次

<inline-toc preview="3"></inline-toc>

## 目的

福岡周辺のiPhoneユーザーが、検索や比較に時間を使わず、「今から使える時間」と興味に合う日帰りツーリング先を決められるかを、最小の製品で検証する。

本書はRD-01〜RD-12の決定を一つに統合し、今後作成する基本設計書、データ契約、実装、試験、限定β判定の基準とする。

## 背景

既存サービスは検索型・地図型が中心であり、ユーザー自身が候補を比較して時間内に帰れるかを判断する必要がある。本MVPは目的地検索ではなく、現在地、利用可能時間、興味、高速道路利用可否から時間内候補を最大5件提示する。

価値検証前に内蔵ナビ、Android、オフライン地図、高度な個人化を実装すると、主要仮説と関係の薄い開発・運用コストが増える。そのため、iOS限定βと外部ナビ連携に責任範囲を絞る。

## ゴール

- 対象ユーザー、検証仮説、KPI、成功・再検証・中止基準が一意である。
- 主要ユースケース3件と、位置拒否、候補0件、外部障害を含む受入条件がある。
- MVP対象、対象外、外部ナビとの責任境界が明確である。
- 画面フロー、入力・表示項目、主要状態が確定している。
- 推薦ルール、時間計算、API v1、エラー・タイムアウト契約が確定している。
- Spot taxonomy、Source/Freshness、匿名行動イベントの論理スキーマが確定している。
- 地図、ルーティング、天気、道路情報、外部POIの採否と利用条件がある。
- 位置情報、行動データ、同意、保存期間、削除、App Store申告方針がある。
- 基本設計へ渡す構成、非機能要件、費用上限案、実装順、リリースゲートがある。
- 未決事項に責任者と決定期限がある。

### 2. 対象ユーザーと検証仮説（RD-01）

#### 2.1 対象ユーザー

- 福岡市および周辺から日帰りツーリングをするiPhoneユーザー。
- 仕事終わりや休日に2〜4時間程度走りたいが、行き先決定を負担に感じる人。
- 年齢、車種、排気量、経験年数による利用制限は設けない。
- 排気量別の道路制約はMVPで扱わないため、原付・125cc以下向けの経路保証は行わない。

#### 2.2 解決する場面

「走れる時間は決まっているが、検索・比較して行き先を決めるのが面倒」という出発前の場面を解決する。走行開始後の経路案内は外部ナビの責任範囲とする。

#### 2.3 検証仮説

> 福岡周辺のiPhoneユーザーにとって、検索結果を自分で比較するより、利用可能時間と興味から時間内候補を提案される方が、短時間で目的地を決めて出発しやすい。

### 3. リリース形態、KPI、判定（RD-01）

#### 3.1 リリース形態

- TestFlightによる招待制限定β。
- 募集人数30人、検証期間4週間。
- 有効推薦セッション100件を最小判定母数とする。
- 4週間で100件に満たない場合は最大2週間延長する。
- App Store一般公開は限定βの継続判断後に別途承認する。

#### 3.2 主要ファネル

```text
recommendation_view → spot_selected → route_started
```

- `recommendation_view`: 候補が1件以上表示された推薦セッションごとに1回。
- `spot_selected`: 同一セッションで「ここに行く」が押された場合に1回。
- `route_started`: Apple Mapsへの引き渡し要求が成功した場合に1回。
- 同一セッション内の再試行は各転換率へ重複計上しない。
- 候補0件、位置権限拒否、API失敗は主要ファネルの分母から除外し、品質指標へ計上する。

#### 3.3 成功基準

| 指標 | 成功 | 再検証 | 中止候補 |
|---|---:|---:|---:|
| `spot_selected / recommendation_view` | 35%以上 | 20%以上35%未満 | 20%未満 |
| `route_started / recommendation_view` | 20%以上 | 10%以上20%未満 | 10%未満 |
| 候補表示成功率 | 95%以上 | 90%以上95%未満 | 90%未満 |
| 候補表示時間 p95 | 5秒以内 | 8秒以内 | 8秒超 |

- 成功: 主要KPIを満たし、重大な安全・データ品質問題がなければ継続する。
- 再検証: UX、候補品質、募集導線を分析し、2週間以内の改善実験を1回行う。
- 中止候補: 有効100セッション以上で `route_started` が10%未満、かつインタビューでも価値が支持されない場合は拡大を止める。
- 安全上の重大問題、データ利用条件違反、運用不能が判明した場合は母数に関係なく停止する。

### 4. ユースケースと共通業務ルール（RD-02）

#### 4.1 共通ルール

- 出発地と帰着地は現在地とし、同一地点へ戻る日帰り往復に限定する。
- 必須入力は現在地、利用可能時間、興味、高速道路利用可否。
- 興味は1件以上選ぶ。`おまかせ` を選んだ場合は他の興味を同時選択しない。
- 利用可能時間は `1時間 / 2時間 / 3時間 / 4時間 / 半日（6時間） / 1日（10時間）`。
- 任意出発地点、帰着時刻、排気量、給油・食事の旅程組込みはMVP後とする。
- 条件を満たす候補を最大5件表示し、件数を埋めるために時間条件を自動緩和しない。

#### 4.2 UC01 仕事終わりに2時間走る

1. 「現在地から探す」を選択する。
2. 位置情報を許可し、2時間、興味、高速利用可否を入力する。
3. 2時間内の候補、推薦理由、合計所要時間、注意情報を確認する。
4. 候補を選び、Apple Mapsへ目的地を渡す。

#### 4.3 UC02 休日午前に4時間走る

UC01と同じ導線で利用可能時間を4時間とする。時間内の候補について、興味一致だけでなく候補カテゴリの多様性を持たせる。

#### 4.4 UC03 目的を指定して走る

`海 / 景色 / 山 / ワインディング / カフェ / 食事 / 温泉 / 道の駅 / 夜景 / 歴史・観光` から1件以上を選び、一致タグと推薦理由を候補へ表示する。

#### 4.5 共通例外

| 例外 | 期待動作 |
|---|---|
| 位置権限未決定 | 「現在地から探す」を押した時だけ `When In Use` を要求する |
| 位置権限拒否 | 必要理由、再試行、設定アプリへの導線を表示する |
| 位置取得失敗 | 再試行を表示し、前回位置を無断利用しない |
| 候補0件 | 時間、興味、高速可否の変更導線を表示する |
| 推薦API失敗 | 再試行可能なエラーを表示し、古い結果を新規結果として表示しない |
| 一部経路失敗 | 失敗候補を除外し、残る候補と警告を表示する |
| 全経路失敗 | 候補0件と区別して外部サービス障害を表示する |
| Apple Maps起動失敗 | 目的地座標のコピーを提示する |

### 5. MVPスコープと責任境界（RD-03）

#### 5.1 MVP必須

- 初回説明、位置権限要求、検索条件入力。
- 候補最大5件、詳細、候補ピン、概要ルート、推薦理由、予測所要時間、鮮度表示。
- `興味あり / 今回は違う / 訪問済み / ここに行く` の操作。
- Apple Mapsへの目的地引き渡し。
- 同意したβユーザーの匿名イベント計測。
- 候補0件、権限拒否、タイムアウト、部分障害、外部ナビ失敗への対応。
- 走行中の操作を促さない注意表示。
- WeatherKitによる候補地点の天気警告。天気は推薦のハード条件にしない。

#### 5.2 MVP対象外

- アカウント、複数端末同期、任意出発地点、帰着時刻指定、車両・排気量プロフィール。
- アプリ内ターンバイターンナビ、走行追跡、走行完了判定、オフライン地図。
- リアルタイム渋滞最適化、アプリ内のリアルタイム道路規制統合。
- 給油・食事を含む旅程、複数日、予約。
- Android、iPad最適化、CarPlay / Android Auto。
- UGC、SNS、通知、ML / LLM推薦。
- Google Places由来コンテンツの表示・Canonical DBへの保存。

#### 5.3 責任境界

```text
アプリ
  現在地取得 → 条件入力 → 候補提案 → 詳細・概要ルート → 目的地引き渡し

Apple Maps
  最新ルート選択 → 走行案内 → 走行中の経路変更 → 到着
```

- 所要時間と帰着予想は予測であり保証しない。
- 交通規制、天候、現地標識は最新情報を優先する。
- Apple Maps起動後の走行・帰着は追跡しない。

### 7. UXフローと画面要件（RD-05）

#### 7.1 画面フロー

```text
初回説明
  ↓
検索条件
  ├─ 位置権限拒否 → 理由説明・設定導線
  └─ 現在地取得
       ↓
時間 → 興味 → 高速可否 → 候補を探す
       ↓
候補一覧 ── 0件／障害 → 条件変更・再試行
       ↓
候補詳細 → フィードバック
       ↓
安全確認 → Apple Maps
```

#### 7.2 画面一覧

| ID | 画面 | 必須要素 |
|---|---|---|
| S01 | 初回説明 | 提案内容、時間は予測、安全上の注意、開始ボタン |
| S02 | 検索条件 | 現在地状態、時間、興味、高速可否、検索ボタン |
| S03 | 候補一覧 | 最大5件、名前、タグ、合計時間、帰着予想、理由、警告、鮮度 |
| S04 | 候補詳細 | 概要、MapKit、概要ルート、時間内訳、天気、営業時間、出典・鮮度、フィードバック |
| S05 | 外部ナビ確認 | 最新情報優先の注意、Apple Maps起動、キャンセル |
| S06 | プライバシー設定 | 分析同意、匿名データ削除、Privacy Policyリンク |

#### 7.3 低忠実度モック

```text
┌─────────────────────────┐
│ 行き先を見つける        │
│ 現在地  [取得済み]      │
│ 時間    [2h][4h][半日]  │
│ 興味    [海][景色][Cafe]│

┌─────────────────────────┐

└─────────────────────────┘
```

#### 7.4 UI受入条件

- S01からS05まで片手操作とVoiceOverで主要操作へ到達できる。
- Dynamic Typeで本文を拡大しても主要CTAが失われない。
- 色だけで選択、警告、エラーを伝えない。
- 候補カードの時間は `往復 + 滞在 + 帰着余裕` を明示する。
- ローディング中の重複送信を防ぐ。
- エラーは技術語を避け、原因区分、再試行可否、次の操作を示す。
- スワイプ操作を必須にせず、すべてボタンでも完了できる。
- 走行中利用を前提とせず、Apple Maps移行後に本アプリの操作を促さない。

### 8. 推薦・時間計算（RD-06）

#### 8.1 時間定義

```text
estimated_total_minutes
  = outbound_minutes
  + stay_minutes
  + return_minutes
  + return_buffer_minutes
```

- `return_buffer_minutes` は `max(15分, ceil((往路 + 復路) × 10% / 5分) × 5分)`。
- ハード条件は `estimated_total_minutes <= available_minutes`。
- 往路・復路は個別に計算し、同一時間と仮定しない。
- 営業時間が「閉店」と確定する候補は除外する。営業時間不明は警告して残す。
- 経路を取得できない候補は除外する。
- 天気はハード条件にせず、警告と最大10点の減点に使う。

#### 8.2 候補抽出

1. 現在地から片道180分以内のCanonical Spotを位置検索する。
2. 経路と所要時間を取得する。
3. 時間、営業状態、経路取得可否でハードフィルタする。
4. 下記スコアを計算し、決定論的に並べる。
5. 同一カテゴリは最大2件を目安に多様性を調整する。
6. 上位5件を返す。

#### 8.3 スコア v1

| 要素 | 点数 | 規則 |
|---|---:|---|
| 興味一致 | 0〜40 | 選択タグとの一致率。`any` は20点固定 |
| 時間適合 | 0〜25 | 利用可能時間を有効活用しつつ余裕を残す候補を優先 |
| 未訪問 | 0または15 | `visited` がなければ15点 |
| データ信頼度 | 0〜10 | 必須属性のconfidence平均 |
| 編集人気度 | 0〜10 | β用の手動優先度。根拠を管理する |
| 天気警告 | 0〜-10 | 警告1件につき-5、下限-10 |

- `not_interested` は同一セッション中の再表示を抑止し、β全期間の永久除外には使わない。
- 同点は `score desc → estimated_total_minutes asc → spot_id asc` で固定する。
- 推薦理由は上位寄与要素から最大3件生成する。

#### 8.4 固定回帰ケース

- 2時間・海・高速なし: 時間内の海候補が優先される。
- 4時間・山・高速可: 山候補が入り、閉店確定Spotは出ない。
- 1時間・温泉: 条件該当がなければ空配列を返す。
- 訪問済みと未訪問が同条件: 未訪問が上位になる。
- 1件だけ経路障害: 残候補と `PARTIAL_ROUTE_FAILURE` を返す。
- 全件経路障害: 503を返し、候補0件扱いにしない。
- 同一入力・同一データ版: 同順位を返す。

### 9. API契約（RD-06）

機械可読な正本は [mvp-openapi-v1.yaml](mvp-openapi-v1.yaml) とする。

#### 9.1 エンドポイント

- `POST /v1/recommendations`: 推薦を生成する。
- `POST /v1/interactions`: 同意済みの匿名イベントを最大50件まとめて送る。
- `DELETE /v1/installations/{installation_id}/data`: 匿名行動データ削除を要求する。

#### 9.2 共通契約

- HTTPSのみ、JSONはUTF-8。
- エラーは `application/problem+json` とし、機械判定用 `code` と `request_id` を返す。
- 推薦のサーバ処理期限は4秒、iOSクライアントのタイムアウトは5秒。
- イベントはクライアント生成UUIDの `event_id` で冪等にする。
- 候補0件は200と空配列、依存障害は503または504で区別する。
- 503、504、通信断だけ再試行対象とし、指数バックオフで最大1回自動再試行する。
- APIレスポンスに秘密情報、内部例外、正確なDB識別子を含めない。

### 10. Spot範囲・taxonomy・データソース（RD-07）

#### 10.1 初期範囲と収集順

- βの出発地域は福岡市内。
- 候補母集団は福岡市中心部から片道180分以内を目安とする。
- まず実データ20件でData Contractと欠損率を確認する。
- 成立確認後に100〜300件へ拡大し、限定β開始時は検証済み100件以上を必須とする。

#### 10.2 taxonomy v1

主カテゴリは1件、興味タグは複数件を許可する。

主カテゴリ:

```text
scenic_view
coast
mountain
cafe
restaurant
onsen
roadside_station
historic_site
tourist_attraction
```

興味タグ:

```text
scenic / sea / mountain / winding / cafe / food
onsen / roadside_station / night_view / historic
```

`winding` は道路曲率による自動判定をMVPでは行わず、根拠を持つ手動タグまたは公的説明に限定する。

#### 10.3 必須属性

- ID、名称、主カテゴリ、緯度経度、滞在目安、タグ。
- 出典、原典ID、ライセンス、取得日時、最終確認日時、信頼度。
- 営業時間、駐車場、二輪可否、概要はnullableとし、不明を虚偽の値で埋めない。
- 画像は権利と配信方法を確認できるものだけ使用する。確認できるまでプレースホルダーを使う。

#### 10.4 ソース方針

| ソース | 役割 | 保存 | 欠損時 |
|---|---|---|---|
| OSM Data | 座標、分類、道路、基本属性 | ODbLと帰属条件を満たして保存 | 公共データまたは手動確認 |
| 自治体・施設公式オープンデータ | 正式名称、説明、営業時間、駐車 | 各ライセンス単位で判定 | nullable、公式URLを案内 |
| 手動確認 | 誤り訂正、滞在目安、二輪可否、優先度 | 確認者・根拠・日時を保存 | 未確認として表示 |
| Google Places | MVP不採用 | Place IDを含めCanonicalに取り込まない | OSM・公共・手動で運用 |

OSMデータはODbLであり帰属が必要である。OSMの標準タイルサーバはデータ取得元ではなく、バルク取得やオフライン利用を前提にできない。本アプリの地図表示にはMapKitを使う。[OpenStreetMap Copyright](https://www.openstreetmap.org/copyright)、[OSM Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/)

Google Placesはコンテンツの事前取得・保存に制約があり、Places結果を地図に表示する場合はGoogle Map上での表示要件もある。MapKit中心のMVPでは混在させず不採用とする。[Google Places policies](https://developers.google.com/maps/documentation/places/web-service/policies)

#### 10.5 収集・更新手順

```text
候補抽出 → Source保存 → ライセンス検査 → 正規化
→ 名寄せ候補生成 → 手動レビュー → Canonical公開
→ 鮮度期限到来 → 再取得または非公開化
```

- ライセンスが不明なレコードは公開しない。
- 必須属性欠損、座標異常、重複未解決のレコードは公開しない。
- 削除元データは論理削除し、Canonicalからの参照を解除できるようにする。

### 11. Spot・Source・Freshness・行動スキーマ（RD-08）

#### 11.1 論理エンティティ

| エンティティ | 主な役割 |
|---|---|
| `spots` | 公開するCanonical Spot。UUIDとPostGIS位置を持つ |
| `spot_sources` | 原典ごとの値、原典ID、URL、ライセンス、取得・確認日時 |
| `spot_field_sources` | Canonicalの各属性がどのSourceを正本にしたか追跡する |
| `tags` / `spot_tags` | taxonomyとSpotの多対多関係 |
| `spot_hours` | 曜日・例外日・不明状態を表現する営業時間 |
| `interaction_events` | 同意済み匿名ユーザーの行動イベント |
| `data_deletion_requests` | 削除要求の受付・完了監査。削除対象本文は保持しない |

#### 11.2 主要制約

- IDはUUID、位置は `GEOGRAPHY(Point, 4326)`。
- 緯度経度はDB位置型を正とし、別カラムへ二重管理しない。
- Canonical Spotと複数Sourceを分離する。
- Source優先度は `手動で確認済み > 施設・自治体公式 > OSM > 未確認手動入力`。
- 100m以内かつ正規化名称類似度0.8以上を重複候補とする。自動統合せず手動承認する。
- `source_type + source_record_id` は一意。
- `interaction_events.event_id` は一意で再送を重複計上しない。

#### 11.3 Freshness

| 属性 | 再確認期限 | 期限超過時 |
|---|---:|---|
| 座標・名称・カテゴリ | 90日 | stale表示、180日で非公開レビュー |
| 営業時間 | 30日 | `unknown` として警告 |
| 駐車場・二輪可否 | 90日 | 不明表示 |
| OSM道路データ | 月次 | ルーティングデータ更新を停止せず警告・運用判断 |
| 天気 | 60分 | 再取得、失敗時は利用不可表示 |
| 経路 | リクエストごと | キャッシュする場合も最大15分 |

#### 11.4 行動イベント

```text
shown / interested / not_interested / visited / selected / route_started
```

- `event_id`、匿名installation ID、session ID、recommendation ID、spot ID、時刻、順位、時間選択、興味コードを保持する。
- 正確な現在地、走行軌跡、Apple Maps内の行動はイベントへ含めない。
- `shown` は画面に実際に表示された候補だけ記録する。

### 12. ルーティングとPOC基準（RD-09）

#### 12.1 条件付き採用

- 第一候補はセルフホストValhalla。
- `motorcycle` profile、`use_trails = 0`、高速可否に応じた `use_highways` をPOCする。
- Valhallaのmotorcycle costingはBETAのため、POC不合格時は `auto` profileへ切り替える。
- OSM由来の二輪規制が完全であるとはみなさず、現地標識優先の注意を必須とする。
- 公開デモサーバを本番依存にしない。

Valhallaはmotorcycle costingと高速・trail調整を提供するが、品質確認が必要である。[Valhalla API reference](https://github.com/valhalla/valhalla-docs/blob/master/turn-by-turn/api-reference.md)、[Valhalla OpenAPI](https://github.com/valhalla/valhalla/blob/master/docs/docs/api/openapi.yaml)

#### 12.2 POC試験

基本設計完了前に福岡周辺15ルートを固定する。

- 市街地短距離3件、海沿い3件、山間部3件、高速利用3件、高速回避3件。
- フェリー、通行不可道路、狭路、トンネル、有料道路を最低1件ずつ含める。
- highway on/off、motorcycle/auto、往路/復路を比較する。

#### 12.3 合格基準

- 15ルートすべてで応答または説明可能なno-routeを返す。
- 明白な歩行者専用路、私道、逆走、通行不能区間を通らない。
- 高速不可のケースで高速道路を使用しない。保証できない場合はその候補を除外する。
- Apple MapsとのETA差が±20%以内のケースが80%以上。
- warm状態のp95応答1.5秒以内、cold状態3秒以内。
- ルート形状をMapKitへ描画できる。
- OSM更新、障害復旧、月額費がRD-12の運用条件内に収まる。

不合格時は、まずValhalla `auto` を評価し、それも不合格なら商用Routing APIを基本設計の変更ADRで選定する。POC完了まではValhallaを確定依存としない。

### 13. 天気・道路情報・安全（RD-10）

#### 13.1 天気

- WeatherKitを採用し、Spot詳細を開いた時に候補地点の時間帯予報を取得する。
- Apple Developer Programに含まれる月50万call枠内で運用し、超過課金は行わない。
- Apple Weatherの帰属表示と法的リンクを表示する。
- ランキングへの影響は最大-10点で、天気だけで候補を除外しない。
- 取得失敗時は推薦を止めず、「天気情報を取得できません。出発前に確認してください」と表示する。

WeatherKitはiOS 16以上で利用でき、Apple Developer Program会員には月50万callが含まれる。[Apple WeatherKit](https://developer.apple.com/weatherkit/)

警告閾値 v1:

- 降水確率50%以上。
- 最大瞬間風速15m/s以上。
- 気温5℃以下または35℃以上。
- Appleが提供する重大気象警報がある。

閾値は安全保証ではなく注意喚起であり、βフィードバックで調整する。

#### 13.2 道路情報

- リアルタイム道路規制のアプリ内統合はMVP対象外とする。
- JARTICオープンデータは月初更新であり、出発直前のリアルタイム規制確認には使わない。
- 候補詳細と外部ナビ確認画面に「道路規制は外部ナビ・JARTIC・現地標識で確認」と表示する。
- 基本設計でJARTIC公式ページへの外部リンク可否と導線を確認する。

[JARTICオープンデータ](https://www.jartic.or.jp/service/opendata/)は交通規制等を提供するが、公開ページ上の更新は毎月月初である。

#### 13.3 安全表示

- 所要時間、天気、営業、道路情報の最終確認時刻を表示する。
- 「予測であり保証ではない」「現地標識を優先」「走行中に操作しない」を初回説明とナビ移行前に表示する。
- 重大警告を色だけで表現しない。
- 安全免責への同意だけで機能上の安全措置を代替しない。

### 14. プライバシー・分析・アカウント（RD-11）

#### 14.1 方針

- アカウントを作成しない。
- 位置権限は `When In Use` のみ。
- 生GPS軌跡、バックグラウンド位置、自宅・勤務先推定を保存しない。
- 広告、第三者広告SDK、クロスアプリトラッキングを使用せず、ATTを要求しない。
- 分析は明示同意したβユーザーだけ有効にし、拒否しても推薦機能を利用できる。

#### 14.2 データ一覧

| データ | 目的 | 保存場所 | 保持期間案 | 第三者送信 |
|---|---|---|---:|---|
| 正確な現在地 | 推薦・経路計算 | 処理中メモリのみ | 応答完了まで | 自社API。自社Valhalla |
| Spot座標 | 地図・天気・外部ナビ | 端末・DB | Spot公開中 | Apple MapKit、WeatherKit、Apple Maps |
| 匿名installation ID | 同意管理、KPI、削除 | 端末・DB | 最終利用から90日 | なし |
| 行動イベント | MVP検証 | DB | 生データ90日 | なし |
| 集計KPI | 継続判断 | DBまたは分析ファイル | 13か月 | なし |
| 運用ログ | 障害・不正対策 | サーバログ | 7日 | 採用監視事業者は基本設計で申告 |

保持期間はRD-05〜12承認時に確定する。ログにはリクエスト本文、緯度経度、削除トークンを記録しない。

#### 14.3 匿名ID・同意・削除

- 初回にランダムなinstallation IDと削除トークンを生成する。
- 分析同意前はinstallation IDをAPIへ送信しない。
- 同意日時、Privacy Policy版、同意状態を端末へ保存する。
- 同意撤回後は新規イベントを停止し、未送信イベントを削除する。
- S06から削除要求を送信し、サーバは7日以内にinstallation IDへ紐づく生イベントを削除する。
- 集計済みで個人・端末へ戻せない統計は削除対象外とし、Privacy Policyに記載する。

#### 14.4 App Store申告

- App Store Connectでは、実装時点の位置情報、識別子、製品操作、診断情報を再棚卸しする。
- 端末だけで処理されサーバへ送られない情報と、サーバへ送る情報を区別する。
- Privacy Policyの公開URLをTestFlight外部テスト前に用意する。
- Appleは位置情報の目的説明と同意、App Storeでのプライバシー情報を求めている。[App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/)

### 15. システム境界と環境（RD-12）

#### 15.1 論理構成

```text
iOS / SwiftUI
  ├─ MapKit / CoreLocation
  ├─ WeatherKit
  ├─ Apple Maps
  └─ HTTPS
       ↓
FastAPI モジュラーモノリス
  ├─ Recommendation
  ├─ Spot Query
  ├─ Interaction / Privacy
  └─ Worker
       ├─ PostgreSQL + PostGIS
       ├─ Valhalla（POC合格後）
       └─ OSM・公共データ取込
```

#### 15.2 環境

- `local`: 固定JSON、ローカルDB、モック外部サービス。
- `staging`: TestFlight、匿名化した実データ、実WeatherKit、POC用Valhalla。
- `production`: 限定β用。stagingと設定・秘密情報・DBを分離する。
- 個人データを本番からlocalへコピーしない。
- インフラ事業者とリージョンは基本設計ADRで決める。PostGIS、暗号化、日次バックアップ、月額上限を必須選定条件とする。

#### 15.3 認証・不正対策

- ユーザー認証は行わない。
- 推薦APIはレート制限を行い、installation IDを認証資格として扱わない。
- 削除要求は端末だけが保持する削除トークンで保護し、サーバにはハッシュを保存する。
- 管理・取込機能は公開APIと分離し、管理者認証を必須にする。
- シークレットをアプリ、リポジトリ、ログへ保存しない。

### 16. 非機能要件（RD-12）

#### 16.1 性能・可用性

- 推薦API p95 5秒以内、サーバ内部処理4秒以内。
- 候補表示成功率95%以上。
- β期間の月間可用性目標99.0%。計画停止は事前通知し集計から分離する。
- 外部サービス部分障害時は、取得済みの安全な候補だけ返すか明示的に失敗する。

#### 16.2 セキュリティ・ログ

- TLS 1.2以上、DBとバックアップの保存時暗号化。
- 最小権限、環境ごとの秘密情報分離、依存関係脆弱性検査。
- 構造化ログにrequest ID、処理時間、結果件数、エラーコードを記録する。
- 緯度経度、削除トークン、WeatherKit認証情報、リクエスト本文をログへ残さない。
- Severity 1・2障害はβを停止し、再開条件を記録する。

#### 16.3 バックアップ・復旧

- PostgreSQLを日次バックアップし、7世代以上保持する。
- 月1回、stagingへリストア試験を行う。
- 目標RPO 24時間、RTO 8時間。
- OSM・公共データは取込元とバージョンから再生成可能にする。

#### 16.4 アクセシビリティ・互換性

- iOS 17以上の現行・一世代前のiPhone画面サイズで確認する。
- VoiceOver、Dynamic Type、コントラスト、44pt以上の主要タップ領域を確認する。
- 正確な位置情報を無効にした端末では取得精度不足を説明し、推薦不能なら再試行を促す。
