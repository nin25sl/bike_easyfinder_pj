# バイク目的地提案アプリ MVP 要件定義・基本設計 決定バックログ

> **目的とゴールの違い**
>
> - **目的** = Why（なぜやるか／何のためか）
> - **ゴール** = Done 条件（何が揃えば完了か／測定可能な完了条件）

## 目次

<inline-toc preview="3"></inline-toc>

## 目的

ユーザーが「今から使える時間」と興味から、時間内に往復できるツーリング先を短時間で決められるという仮説を、最小の実装で検証する。そのために、実装開始後の手戻りにつながる未決事項を先に意思決定し、要件定義と基本設計を止めずに進められる状態を作る。

## 背景

主資料 `docs/requirements/kyushu_touring_app_mvp_requirements.md` は、福岡周辺を初期対象とした iOS / SwiftUI、FastAPI、PostgreSQL + PostGIS、Valhalla、MapKit、ルールベース推薦をMVP案としている。一方、調査資料 `docs/requirements/20260923_first_investigation.md` は、日本全国・iOS/Android、Flutter、GraphHopper、MapLibre等を推奨候補としている。

最短リリースを優先する場合、この差分を未決のまま実装へ持ち込むと、モバイル、地図、ルーティング、API、データ契約の作り直しが発生する。そこで、主資料を優先し、調査資料はリスク・比較候補・将来拡張の判断材料として使う。

## ゴール

### 要件定義の完了条件

- RD-01〜RD-12の決定記録が承認され、未決事項に担当者と期限がある。
- 主要ユースケース3件、MVP対象・対象外、検証仮説、主要KPIが一意に記述されている。
- 画面フローと低忠実度モックにより、現在地取得から外部ナビ起動までの操作が確認できる。
- 実データから作るSpot taxonomy v1、Spot / Source / Freshness schema v1、推薦API契約 v1 が確定している。
- Spot、地図、ルーティング、天気、道路情報の採用・非採用と利用条件が決まっている。
- 位置情報、行動履歴、外部API送信、保存期間、同意・削除方針が決まっている。
- MVPのリリース判定、計測イベント、概算費用、基本設計タスクが承認されている。

### やらないこと

- 内蔵ターンバイターンナビ、オフライン地図、リアルタイム渋滞最適化
- Android、iPad最適化、CarPlay / Android Auto
- UGC、SNS、宿泊・キャンプ予約、複数日ツーリング
- ML / LLM推薦、マイクロサービス化、日本全国への展開

## 本文

### 最短リリースの判断原則

1. `kyushu_touring_app_mvp_requirements.md` を主資料とし、矛盾時は「検証に必要な最小範囲」を採る。
2. 初期テストは福岡周辺100件程度、MVP公開対象は九州7県とし、固定件数より継続収集・更新基盤を優先する。
3. 初期クライアントはiOSのみ、SwiftUI + MapKitを既定案とする。
4. 走行開始後は外部ナビへ連携し、アプリの責任範囲を目的地決定までに限定する。
5. FastAPIのモジュラーモノリス、PostgreSQL + PostGIS、ルールベース推薦を既定案とする。
6. Weather / 道路情報は「取得できなければ注意表示または初回対象外」とし、リリースを止める依存にしない。
7. 判断期限内に反証が出なければ推奨デフォルトを採用し、実装を開始する。

### 意思決定タスク

#### 進捗（2026-09-23）

- **RD-01〜RD-04:** 2026-09-23にプロダクトオーナー承認済み。内容は [MVP要件定義書 v1](mvp-requirements-v1.md) へ統合した。
- **旧成果物:** 旧PRDとADR-001は現行文書ではないため、[garbage](../garbage/) へ退避した。
- **RD-05:** 承認済み。Tinder等のマッチングアプリを参考にしたカード型・逐次提案UX、初回／再訪フロー、3種のリアクション、興味あり一覧を採用する。「興味なし」は永久除外せず、Spot・類似カテゴリ・タグへの負の嗜好シグナルとして推薦スコアを抑制する。
- **RD-06:** 承認済み。`往路 + 滞在 + 復路 + 15分の帰着余裕 <= 利用可能時間` を基本条件とし、APIはRecommendation / Interaction / Privacyの3領域に整理する。RD-05の「興味なし」はハード除外せずソフト抑制として扱う。
- **RD-07:** 承認済み。初期テストは福岡周辺100件程度、MVP公開は九州7県、複数カテゴリ、実データ後のtaxonomy確定、月次自動更新と人間レビューを採用する。
- **RD-08:** 承認済み。Canonical SpotとSourceの分離、属性別出典、一般Web Source、重複候補、月次チェックと属性別Freshnessを採用する。行動イベントは `shown / interested / not_interested / visited / selected / route_started` を基本候補とし、発火条件・重複計上防止は基本設計で確定する。
- **RD-09:** 方針承認済み。アプリ内ルーティングは行わず、推薦用の距離・所要時間のみBackendから取得し、実走行ナビはApple Maps / Google Maps等へ委譲する。ETA ProviderはiOS / Androidに依存しないサーバー向けAPIをPOC比較して基本設計で確定する。
- **RD-10:** 基本原則承認済み。WeatherKitは詳細画面の注意情報に限定し、推薦計算・候補除外には使わない。リアルタイム道路規制は将来版を含めアプリ側対象外とする。属性付与方式、警告発火条件、取得失敗時文言は基本設計で確定する。
- **RD-11:** 条件付き承認。MVPはアカウントなし・匿名installation IDとし、将来のuser ID紐付け、初回分析同意・撤回、匿名データ削除を採用する。具体的保持期間は、正確な現在地は非永続、Recommendation Impression生データ90日、行動履歴24か月、分析イベント12か月、API/Applicationログ30日、Crash/Errorログ90日を初期案とし、最終承認後にPrivacy方針へ固定する。
- **RD-12:** 承認済み。ValhallaをMVP構成・POC・リリースゲートから除外し、九州7県のVer0.1成立、3環境、staging/production同一構成、環境差分管理、監視、バックアップ、月額1万円と費用最小化を採用する。具体サービス、県別判定ケース、監視閾値、復旧優先度、RPO/RTOは基本設計へ正式に引き継ぐ。
- **先行実装:** 承認済み範囲を [iOS MVP骨格](../../../ios/BikeEasyFinder/README.md) として実装済み。SwiftUI、位置権限、条件入力、固定候補、MapKit、Apple Maps連携、主要例外表示を含む。
- **検証状況:** Info.plistとソース構成の静的検証は完了。作業環境がWindowsでSwift/Xcodeを利用できないため、XcodeGenによるプロジェクト生成、iOSビルド、ユニットテスト実行はMacでの確認待ち。
- **次:** RD-11の保持期間を最終承認後、要件定義の未承認事項をクローズする。RD-09のETA Provider選定、九州7県のPOC条件、RD-12の具体インフラ・監視・復旧設計は基本設計で確定する。

#### RD-01 検証仮説・成功指標・リリース対象を確定する

- **優先度 / 期限目安:** P0 / Day 1
- **依存:** なし
- **決めること:** 誰のどの場面を解決するか、MVPで検証する仮説、テスト配布かApp Store公開か、成功・中止基準。
- **推奨デフォルト:** MVP公開対象は九州7県、初期テスト募集は福岡周辺のiPhoneユーザーを優先する。主仮説は「検索ではなく、時間内候補の提案に価値がある」。主要KPIは `recommendation_view → spot_selected → route_started` の転換率。数値目標はテスト人数と期間を決めたうえで設定する。
- **成果物:** PRD v1の「目的・対象・仮説・KPI・リリース形態」。
- **完了条件:** 対象ユーザー、検証期間、募集人数、主要KPI、成功閾値、撤退・継続判断日が承認されている。

#### RD-02 主要ユースケースと利用条件を確定する

- **優先度 / 期限目安:** P0 / Day 1
- **依存:** RD-01
- **決めること:** 仕事終わり2時間、休日午前4時間、目的指定の3ケースについて、開始・終了条件、例外、任意出発地点・帰着時刻・排気量入力の要否。
- **推奨デフォルト:** 現在地、利用可能時間、興味、高速利用可否だけを必須とし、現在地へ戻る日帰り往復に限定する。任意地点、排気量、給油・食事は初回対象外。
- **成果物:** UC01〜UC03の受入条件と共通業務ルール。
- **完了条件:** 各ケースに正常系、位置情報拒否、候補0件、経路取得失敗の期待動作がある。

#### RD-03 MVPスコープと責任境界を確定する

- **優先度 / 期限目安:** P0 / Day 1
- **依存:** RD-01、RD-02
- **決めること:** 候補提示、詳細、地図、フィードバック、外部ナビ連携の範囲。天気・道路情報・アカウントの必須性。
- **推奨デフォルト:** 候補5件、詳細、地図、興味あり／なし／訪問済み／ここに行く、外部ナビ起動まで。アカウントなしの匿名端末ID。天気は天候依存Spotの詳細画面で注意表示し、道路規制は将来版を含めアプリ側対象外とする。
- **成果物:** In / Out一覧と責任境界図。
- **完了条件:** 各機能が `MVP必須`、`条件付き`、`MVP後` のいずれかに分類され、条件付き項目の判断期限がある。

#### RD-04 モバイル・地図・ナビ技術を確定する

- **優先度 / 期限目安:** P0 / Day 1
- **依存:** RD-03
- **決めること:** SwiftUI対Flutter、MapKit対MapLibre、内蔵ルート表示の粒度、外部ナビ連携先。
- **推奨デフォルト:** iOS / SwiftUI / MapKit / CoreLocation。アプリ内は候補ピンと概要ルート表示に限定し、走行はApple MapsまたはGoogle Mapsへ渡す。Flutter / Android / MapLibreはMVP後。
- **成果物:** ADR-001「Mobile / Map / Navigation」。
- **完了条件:** 対象OS、最低OS版、地図SDK、位置権限、外部ナビ連携、採用しない候補と再検討条件が記録されている。

#### RD-05 UXフローと画面要件を確定する

- **優先度 / 期限目安:** P0 / Day 2
- **依存:** RD-02〜RD-04
- **決めること:** 初回説明、位置権限要求のタイミング、時間・興味入力、候補表示形式、詳細、0件・エラー表示、走行中操作抑止。
- **推奨デフォルト:** 「現在地から探す」操作後に権限要求し、時間→興味→高速可否→1件ずつの提案カード→詳細→ここに行く→外部ナビとする。初回説明は初回だけ、再訪時は前回条件の再利用・変更と興味あり一覧を提示する。3種のリアクションはボタン操作でも成立させる。
- **成果物:** 画面一覧、画面遷移、低忠実度モック、UI受入条件。
- **完了条件:** UC01〜UC03と主要例外がモック上で最後まで通り、入力項目と表示項目が確定している。

#### RD-06 推薦・時間計算・API契約を確定する

- **優先度 / 期限目安:** P0 / Day 2
- **依存:** RD-02、RD-03、RD-05
- **決めること:** `total_duration` の定義、帰着余裕、候補数、スコア項目、営業時間・天気・リアクションの扱い、MVP全体のAPI一覧と責務、APIメソッド、エラー契約。
- **推奨デフォルト:** `往路 + 滞在 + 復路 + 15分の帰着余裕 <= 利用可能時間` をハード条件とする。興味なし・訪問済みは基本的に除外する。公開APIはRecommendation、Interaction、Privacyの3領域に絞り、画面対応を示してから個別OpenAPIをレビューする。
- **成果物:** 推薦ルール v1、OpenAPI契約 v1、固定テストケース。
- **完了条件:** 代表入力、候補0件、部分的外部API障害、タイムアウトのレスポンスと、決定論的な期待順位が定義されている。

#### RD-07 Spot対象範囲・taxonomy・データソースを確定する

- **優先度 / 期限目安:** P0 / Day 2
- **依存:** RD-02、RD-03
- **決めること:** 福岡周辺100件程度の初期テスト、九州7県の継続収集方法、分類用原情報、複数カテゴリ、幅広い公開Web情報源、変動情報の確認元、月次更新、人間レビュー。
- **推奨デフォルト:** 候補発見は公開Webの幅広い情報源を使い、変動情報は信頼できる情報源で確認する。カテゴリ・タグは先に固定せず、原情報を保存して実データ分析後に確定する。Google PlacesはMVP不採用とする。
- **成果物:** Data Contract v1、情報源台帳、継続収集・月次更新設計、レビューキュー設計、実データ分析後のSpot taxonomy v1。
- **完了条件:** 福岡周辺100件程度で収集から更新までを検証し、九州7県の収集基盤、属性別出典、複数カテゴリ、自動確認不能時の人間レビューが成立している。

#### RD-08 Spot / Source / Freshness / 行動履歴スキーマを確定する

- **優先度 / 期限目安:** P0 / Day 3
- **依存:** RD-06、RD-07
- **決めること:** ID、位置型、営業時間、駐車・二輪可否、タグ、出典、ライセンス、鮮度、信頼度、名寄せ、匿名ユーザー行動の項目。
- **決定:** 条件付き承認。PostgreSQL + PostGIS、UUID、`GEOGRAPHY(Point, 4326)`、Canonical Spotと複数Sourceを分離し、属性別に採用Sourceを追跡する。一般WebをSourceとして収集可能にする。名寄せは100m以内かつ名称類似度0.8以上を重複候補とし、自動統合しない。全Canonical Spot／Sourceを月1回チェックし、属性別Freshness期限とは分離する。
- **保留:** `interaction_events` はRD-05のカード型UX修正後にイベント名・発火条件・重複計上を再レビューする。
- **成果物:** ER図、DDL案、データ辞書、名寄せ・鮮度ルール。
- **完了条件:** RD-06のAPI応答を生成でき、出典追跡、削除、再取り込み、重複レビューが可能である。

#### RD-09 推薦用の移動時間推定と外部Map連携を確定する

- **優先度 / 期限目安:** P0 / Day 3
- **依存:** RD-04、RD-06、RD-07
- **決定:** Bike EasyFinderはツーリング先の提案に責任を持ち、アプリ内のルート検索・ターンバイターンナビゲーションは行わない。推薦判定に必要な距離・所要時間だけを取得し、走行時のルート検索・ナビはApple MapsまたはGoogle Mapsへ委譲する。Valhallaと独自ルーティングはMVP対象外とし、独自ルート、ワインディング優先、海沿い優先、市街地回避が必要になった段階だけ再評価する。
- **決めること:** Apple MapKit、Google Routes API、その他APIのどれを推薦用推定に使うか。精度、料金、iOSとの親和性、API・利用規約上の制約、障害時動作、推定値と外部Mapナビ結果の許容差を比較する。外部Mapへ渡す目的地座標、Spot名称、出発地、必要に応じた経由地と、Apple Maps優先・Google Maps選択・未インストール時のUXを定義する。
- **POC範囲:** 福岡限定ではなく九州7県。各県で都市部、山間部、海沿い、高速利用など条件の異なるケースを最低1件以上含める。県別件数と総件数は取得方式の候補確定時に固定する。
- **成果物:** ADR-002「Travel Time Estimation / External Maps」、Provider比較表、外部Map連携仕様、九州7県POC試験票。
- **完了条件:** 九州7県で利用可能時間を考慮した候補を返せる。推薦用の距離・所要時間を実利用上致命的でない待ち時間で取得できる。Apple Maps／Google Mapsを正常起動し、正しいSpotへ遷移できる。推定値と外部Map結果の許容差、Provider障害時動作、費用・利用制約が承認されている。

#### RD-10 天気・道路情報・安全表示を確定する

- **優先度 / 期限目安:** P0（採否判断） / Day 3
- **依存:** RD-03、RD-06
- **決定:** 修正条件付き承認。WeatherKitは天候依存属性を持つSpotの詳細表示時に、現在から訪問想定時間帯までの注意情報を取得する用途に限定する。天気は推薦ランキング、候補除外に使用しない。リアルタイム道路規制とJARTIC統合はMVP・将来版ともアプリ側対象外とし、実際のルート判断はApple Maps／Google Maps／現地標識へ委譲する。最終確認時刻はUI表示せず、Freshnessのみ内部管理する。
- **未確定:** 天候依存属性の手動付与／AI判定と段階数、雨・曇り・降水確率・風・気温等のポップアップ発火条件、WeatherKit取得失敗時の文言、S07で天気注意を再表示するか。
- **成果物:** 天候依存属性仕様、詳細画面ポップアップ仕様、WeatherKitフォールバック文言、RD-05と整合したナビ移行前安全確認仕様。
- **完了条件:** 属性付与方式、発火条件、障害時UI、ナビ移行前表示が承認され、天気が推薦計算・候補除外へ影響しないテストが定義されている。

#### RD-11 プライバシー・分析・アカウント方針を確定する

- **優先度 / 期限目安:** P0 / Day 3
- **依存:** RD-01、RD-03、RD-08
- **決定:** 条件付き承認。MVPではアカウントを作らず匿名installation IDで識別する。正確な現在地は利用時の推薦処理だけに使い永続保存しない。利用分析は全ユーザーを基本対象とするが、初回に目的を明示して同意を取得し、撤回手段を提供する。広告・クロスアプリトラッキングには使わず、ATT不要の自社サービス改善用分析に限定する。現行の削除トークン方式でinstallation IDに紐づく生データを削除可能にする。保持期間はデータごとに決める。
- **将来設計:** 課金、Web版、複数端末同期、履歴引き継ぎの段階でuser IDを導入できるよう、1つのアカウント主体に複数installation IDを後から紐付け可能にする。
- **未決:** アカウント導入時の履歴移行・紐付け時点、課金方式、RD-05依存の行動イベント、データ別の具体的保持期間、削除トークン消失時の救済策。
- **残作業:** 初回同意フロー、分析対象データと目的、同意撤回画面・処理を設計する。全保存データについて目的、保存場所、保持期間、削除条件、第三者送信を棚卸しし、実装完了時にApp Store Connect申告を再確認する。
- **成果物:** Privacy方針 v1、データ一覧、イベント計測仕様、Privacy Policy草案。
- **完了条件:** 残作業が完了し、収集項目ごとに目的、保存場所、保持期間、第三者送信、削除方法が決まり、App Store申告に転記できる。

#### RD-12 基本設計・費用・リリース計画を承認する

- **優先度 / 期限目安:** P0 / Day 4
- **依存:** RD-01〜RD-11

### リスク

- **データ利用条件:** OSM TileとOSM Dataを混同しない。Google Placesは永続保存を前提にしない。採用前に公式規約を確認する。
- **所要時間の差:** 推薦時の推定と外部MapのETAに差が出る可能性がある。許容差を定義し、九州7県POCで計測する。
- **「時間内」の過信:** 所要時間は予測であり保証ではない。帰着余裕と免責表示を持たせる。
- **スコープ膨張:** 調査資料の全国・Android・リアルタイム・オフライン・UGCはMVP後に固定する。
- **プライバシー:** 正確な位置履歴を長期保存しない。収集前に目的・保持期間・削除方法を確定する。
- **一人開発:** 外部サービスのセルフホストや複数クライアントを増やすと運用が先に破綻する。マネージド利用または機能延期の判断期限を設ける。
