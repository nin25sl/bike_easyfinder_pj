# バイク目的地提案アプリ MVP 要件定義・基本設計 決定バックログ

> **目的とゴールの違い**
>
> - **目的** = Why（なぜやるか／何のためか）
> - **ゴール** = Done 条件（何が揃えば完了か／測定可能な完了条件）

## 目次

<inline-toc preview="3"></inline-toc>

## 目的

ユーザーが「今から使える時間」と興味から、時間内に往復できるツーリング先を短時間で決められるという仮説を、最小の実装で検証する。そのために、実装開始後の手戻りにつながる未決事項を先に意思決定し、要件定義と基本設計を止めずに進められる状態を作る。

## 背景

主資料 `docs/requirements/kyushu_touring_app_mvp_requirements.md` は、福岡周辺を初期対象とした iOS / SwiftUI、FastAPI、PostgreSQL + PostGIS、Valhalla、MapKit、ルールベース推薦をMVP案としている。一方、調査資料 `docs/requirements/20260923_first_investigation.md` は、日本全国・iOS/Android、Flutter、GraphHopper、MapLibre等を推奨候補としている。

最短リリースを優先する場合、この差分を未決のまま実装へ持ち込むと、モバイル、地図、ルーティング、API、データ契約の作り直しが発生する。そこで、主資料を優先し、調査資料はリスク・比較候補・将来拡張の判断材料として使う。

## ゴール

### 要件定義の完了条件

- RD-01〜RD-12の決定記録が承認され、未決事項に担当者と期限がある。
- 主要ユースケース3件、MVP対象・対象外、検証仮説、主要KPIが一意に記述されている。
- 画面フローと低忠実度モックにより、現在地取得から外部ナビ起動までの操作が確認できる。
- Spot taxonomy v1、Spot / Source / Freshness schema v1、推薦API契約 v1 が確定している。
- Spot、地図、ルーティング、天気、道路情報の採用・非採用と利用条件が決まっている。
- 位置情報、行動履歴、外部API送信、保存期間、同意・削除方針が決まっている。
- MVPのリリース判定、計測イベント、概算費用、基本設計タスクが承認されている。

### やらないこと

- 内蔵ターンバイターンナビ、オフライン地図、リアルタイム渋滞最適化
- Android、iPad最適化、CarPlay / Android Auto
- UGC、SNS、宿泊・キャンプ予約、複数日ツーリング
- ML / LLM推薦、マイクロサービス化、九州全域データ完成

## 本文

### 最短リリースの判断原則

1. `kyushu_touring_app_mvp_requirements.md` を主資料とし、矛盾時は「検証に必要な最小範囲」を採る。
2. 初期地域は福岡市から日帰り圏、Spotは100〜300件の管理可能な母集団から始める。
3. 初期クライアントはiOSのみ、SwiftUI + MapKitを既定案とする。
4. 走行開始後は外部ナビへ連携し、アプリの責任範囲を目的地決定までに限定する。
5. FastAPIのモジュラーモノリス、PostgreSQL + PostGIS、ルールベース推薦を既定案とする。
6. Weather / 道路情報は「取得できなければ注意表示または初回対象外」とし、リリースを止める依存にしない。
7. 判断期限内に反証が出なければ推奨デフォルトを採用し、実装を開始する。

### 意思決定タスク

#### 進捗（2026-09-23）

- **RD-01〜RD-04:** 2026-09-23にプロダクトオーナー承認済み。内容は [MVP要件定義書 v1](mvp-requirements-v1.md) へ統合した。
- **旧成果物:** 旧PRDとADR-001は現行文書ではないため、[garbage](../garbage/) へ退避した。
- **RD-05〜RD-12:** [MVP要件定義書 v1](mvp-requirements-v1.md) と [OpenAPI v1](mvp-openapi-v1.yaml) に決定案を反映済み。A-01〜A-04をプロダクトオーナー承認待ち。
- **先行実装:** 承認済み範囲を [iOS MVP骨格](../../../ios/BikeEasyFinder/README.md) として実装済み。SwiftUI、位置権限、条件入力、固定候補、MapKit、Apple Maps連携、主要例外表示を含む。
- **検証状況:** Info.plistとソース構成の静的検証は完了。作業環境がWindowsでSwift/Xcodeを利用できないため、XcodeGenによるプロジェクト生成、iOSビルド、ユニットテスト実行はMacでの確認待ち。
- **次:** A-01〜A-04の承認後に要件定義書の `draft` を解除し、基本設計書を作成する。Spotサンプル20件とValhalla 15ルートPOCは基本設計と並行して実施する。

#### RD-01 検証仮説・成功指標・リリース対象を確定する

- **優先度 / 期限目安:** P0 / Day 1
- **依存:** なし
- **決めること:** 誰のどの場面を解決するか、MVPで検証する仮説、テスト配布かApp Store公開か、成功・中止基準。
- **推奨デフォルト:** 福岡周辺のiPhoneユーザー向け限定β。主仮説は「検索ではなく、時間内候補の提案に価値がある」。主要KPIは `recommendation_view → spot_selected → route_started` の転換率。数値目標はテスト人数と期間を決めたうえで設定する。
- **成果物:** PRD v1の「目的・対象・仮説・KPI・リリース形態」。
- **完了条件:** 対象ユーザー、検証期間、募集人数、主要KPI、成功閾値、撤退・継続判断日が承認されている。

#### RD-02 主要ユースケースと利用条件を確定する

- **優先度 / 期限目安:** P0 / Day 1
- **依存:** RD-01
- **決めること:** 仕事終わり2時間、休日午前4時間、目的指定の3ケースについて、開始・終了条件、例外、任意出発地点・帰着時刻・排気量入力の要否。
- **推奨デフォルト:** 現在地、利用可能時間、興味、高速利用可否だけを必須とし、現在地へ戻る日帰り往復に限定する。任意地点、排気量、給油・食事は初回対象外。
- **成果物:** UC01〜UC03の受入条件と共通業務ルール。
- **完了条件:** 各ケースに正常系、位置情報拒否、候補0件、経路取得失敗の期待動作がある。

#### RD-03 MVPスコープと責任境界を確定する

- **優先度 / 期限目安:** P0 / Day 1
- **依存:** RD-01、RD-02
- **決めること:** 候補提示、詳細、地図、フィードバック、外部ナビ連携の範囲。天気・道路情報・アカウントの必須性。
- **推奨デフォルト:** 候補5件、詳細、地図、興味あり／なし／訪問済み／ここに行く、外部ナビ起動まで。アカウントなしの匿名端末ID。天気は警告表示、道路規制は取得可否を調査して初回の必須条件から外す。
- **成果物:** In / Out一覧と責任境界図。
- **完了条件:** 各機能が `MVP必須`、`条件付き`、`MVP後` のいずれかに分類され、条件付き項目の判断期限がある。

#### RD-04 モバイル・地図・ナビ技術を確定する

- **優先度 / 期限目安:** P0 / Day 1
- **依存:** RD-03
- **決めること:** SwiftUI対Flutter、MapKit対MapLibre、内蔵ルート表示の粒度、外部ナビ連携先。
- **推奨デフォルト:** iOS / SwiftUI / MapKit / CoreLocation。アプリ内は候補ピンと概要ルート表示に限定し、走行はApple MapsまたはGoogle Mapsへ渡す。Flutter / Android / MapLibreはMVP後。
- **成果物:** ADR-001「Mobile / Map / Navigation」。
- **完了条件:** 対象OS、最低OS版、地図SDK、位置権限、外部ナビ連携、採用しない候補と再検討条件が記録されている。

#### RD-05 UXフローと画面要件を確定する

- **優先度 / 期限目安:** P0 / Day 2
- **依存:** RD-02〜RD-04
- **決めること:** 初回説明、位置権限要求のタイミング、時間・興味入力、候補表示形式、詳細、0件・エラー表示、走行中操作抑止。
- **推奨デフォルト:** 「現在地から探す」操作後に権限要求し、時間→興味→高速可否→候補カード→詳細→ここに行く→外部ナビの1本の導線にする。スワイプは必須にせずボタン操作でも成立させる。
- **成果物:** 画面一覧、画面遷移、低忠実度モック、UI受入条件。
- **完了条件:** UC01〜UC03と主要例外がモック上で最後まで通り、入力項目と表示項目が確定している。

#### RD-06 推薦・時間計算・API契約を確定する

- **優先度 / 期限目安:** P0 / Day 2
- **依存:** RD-02、RD-03、RD-05
- **決めること:** `total_duration` の定義、帰着余裕、候補数、スコア項目、営業時間・天気・既訪問の扱い、APIメソッド、エラー契約。
- **推奨デフォルト:** `往路 + 滞在 + 復路 + 15分の帰着余裕 <= 利用可能時間` をハード条件とする。興味一致、距離、未訪問、人気度をルールで順位付けし、天気は減点または警告。`POST /v1/recommendations` と `POST /v1/interactions` に絞る。
- **成果物:** 推薦ルール v1、OpenAPI契約 v1、固定テストケース。
- **完了条件:** 代表入力、候補0件、部分的外部API障害、タイムアウトのレスポンスと、決定論的な期待順位が定義されている。

#### RD-07 Spot対象範囲・taxonomy・データソースを確定する

- **優先度 / 期限目安:** P0 / Day 2
- **依存:** RD-02、RD-03
- **決めること:** 初期地理範囲、100〜300件の収集方法、カテゴリとタグ、OSM・公共データ・手動データ・Google Placesの役割と保存条件。
- **推奨デフォルト:** 福岡市から現実的な日帰り圏を対象とし、OSM + 公共データ + 手動補正でCanonical Spotを作る。Google Placesは規約・費用確認が終わるまで必須依存にせず、表示時の補完候補とする。
- **成果物:** Data Contract v1、Spot taxonomy v1、ソース別利用条件一覧。
- **完了条件:** 各属性に正本ソース、保存可否、更新方法、欠損時動作があり、100〜300件を取得できる見通しが実データのサンプルで確認されている。

#### RD-08 Spot / Source / Freshness / 行動履歴スキーマを確定する

- **優先度 / 期限目安:** P0 / Day 3
- **依存:** RD-06、RD-07
- **決めること:** ID、位置型、営業時間、駐車・二輪可否、タグ、出典、ライセンス、鮮度、信頼度、名寄せ、匿名ユーザー行動の項目。
- **推奨デフォルト:** PostgreSQL + PostGIS、UUID、`GEOGRAPHY(Point, 4326)`、Canonical Spotと複数Sourceを分離する。名寄せは100m以内かつ名称類似度0.8超、曖昧時は手動確認。行動は `shown / interested / not_interested / visited / selected / route_started` を保存する。
- **成果物:** ER図、DDL案、データ辞書、名寄せ・鮮度ルール。
- **完了条件:** RD-06のAPI応答を生成でき、出典追跡、削除、再取り込み、重複レビューが可能である。

#### RD-09 ルーティング方式とPOC判定基準を確定する

- **優先度 / 期限目安:** P0 / Day 3
- **依存:** RD-04、RD-06、RD-07
- **決めること:** Valhalla対GraphHopper対商用API、motorcycle対auto profile、高速回避、セルフホスト範囲、精度・速度・費用基準。
- **推奨デフォルト:** 主資料どおりValhallaを第一候補にし、福岡周辺10〜20ルートでPOCする。期限内に環境構築または品質条件を満たせなければ、商用APIまたはGraphHopperへ切り替える。
- **成果物:** ADR-002「Routing」、POC試験票。
- **完了条件:** 所要時間、経路の不自然さ、二輪通行不可、高速可否、応答時間、運用費の比較結果と採否がある。

#### RD-10 天気・道路情報・安全表示を確定する

- **優先度 / 期限目安:** P0（採否判断） / Day 3
- **依存:** RD-03、RD-06
- **決めること:** Provider、取得地点・時刻、警告閾値、通行止めの扱い、鮮度表示、安全免責、障害時動作。
- **推奨デフォルト:** 天気は候補地点の降水・風・気温を警告用途で採用し、ランキングへの影響は小さくする。道路情報は信頼できる取得方式が期限内に決まらなければ初回対象外と明示し、外部ナビで最新情報を確認させる。
- **成果物:** Provider比較、採否ADR、警告文言・フォールバック仕様。
- **完了条件:** 採用・非採用、費用、利用規約、更新間隔、障害時UIが承認されている。

#### RD-11 プライバシー・分析・アカウント方針を確定する

- **優先度 / 期限目安:** P0 / Day 3
- **依存:** RD-01、RD-03、RD-08
- **決めること:** 位置情報の収集目的、端末内／サーバ保存、精度、保存期間、外部送信、匿名ID、同意、削除、Analyticsイベント、アカウント有無。
- **推奨デフォルト:** `When In Use` のみ。生のGPS軌跡は保存せず、推薦リクエストの位置は短期ログまたは地域化して保存する。アカウントなし、匿名端末ID、行動イベントは目的と保存期間を限定する。
- **成果物:** Privacy方針 v1、データ一覧、イベント計測仕様、Privacy Policy草案。
- **完了条件:** 収集項目ごとに目的、保存場所、保持期間、第三者送信、削除方法が決まり、App Store申告に転記できる。

#### RD-12 基本設計・費用・リリース計画を承認する

- **優先度 / 期限目安:** P0 / Day 4
- **依存:** RD-01〜RD-11
- **決めること:** システム構成、環境、認証、監視、バックアップ、外部API予算、実装順、リリースゲート。
- **推奨デフォルト:** SwiftUI → HTTPS → FastAPIモジュラーモノリス → PostgreSQL + PostGIS。データ取込はWorkerに分離する。まず固定データでもE2Eを通し、データ収集とPOCを並行する。
- **成果物:** 基本設計 v1、概算費用、実装バックログ、リリースチェックリスト。
- **完了条件:** 構成図、コンポーネント責務、API・DB・外部連携、非機能最小要件、月額上限、P0タスクの順序と担当が承認されている。

### クリティカルパスと並行作業

```text
RD-01 → RD-02 → RD-03 → RD-04 → RD-05
                    ├──────→ RD-06 ──┐
                    └──────→ RD-07 → RD-08 ──┐
RD-04 + RD-06 + RD-07 → RD-09 ───────────────┤
RD-03 + RD-06 → RD-10 ───────────────────────┤
RD-01 + RD-03 + RD-08 → RD-11 ───────────────┤
                                               ↓
                                             RD-12
```

Day 1でプロダクト境界と技術方針を決め、Day 2以降はUX、API、データ契約を並行する。RD-12を待たず、変更コストが低いSwiftUIの画面骨格、固定JSONによるAPIスタブ、福岡Spotのサンプル収集は開始してよい。

### 要件定義後の基本設計タスク

- **BD-01:** コンテキスト図、コンポーネント図、主要シーケンスを作成する。
- **BD-02:** OpenAPI v1、エラーコード、タイムアウト、冪等性、バージョニングを設計する。
- **BD-03:** ER図、DDL、インデックス、位置検索、マイグレーションを設計する。
- **BD-04:** OSM / 公共データ取込、名寄せ、Canonical生成、鮮度更新のジョブを設計する。
- **BD-05:** 推薦パイプライン、ハードフィルタ、ランキング、説明理由を設計する。
- **BD-06:** SwiftUIの状態管理、画面遷移、権限、APIクライアント、外部ナビ連携を設計する。
- **BD-07:** 構成管理、シークレット、ログ、監視、バックアップ、障害時フォールバックを設計する。
- **BD-08:** 固定ペルソナの回帰ケース、E2E、位置情報拒否、候補0件、外部障害の試験を設計する。

### リスク

- **データ利用条件:** OSM TileとOSM Dataを混同しない。Google Placesは永続保存を前提にしない。採用前に公式規約を確認する。
- **ルーティング品質:** 二輪専用profileでも日本の二輪規制を完全には保証できない。POCと注意表示を必須にする。
- **「時間内」の過信:** 所要時間は予測であり保証ではない。帰着余裕と免責表示を持たせる。
- **スコープ膨張:** 調査資料の全国・Android・リアルタイム・オフライン・UGCはMVP後に固定する。
- **プライバシー:** 正確な位置履歴を長期保存しない。収集前に目的・保持期間・削除方法を確定する。
- **一人開発:** 外部サービスのセルフホストや複数クライアントを増やすと運用が先に破綻する。マネージド利用または機能延期の判断期限を設ける。

- 推薦位置・行動ログを保存する期間と分析基盤
- 外部ナビ連携先をApple Mapsだけにするか、Google Mapsも含めるか
