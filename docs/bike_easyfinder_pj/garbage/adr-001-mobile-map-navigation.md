>

## 目的

MVPのモバイル、地図、位置情報、ナビ連携の技術選択を固定し、複数プラットフォーム対応や内蔵ナビによる手戻りを防ぐ。

## 背景

主資料はiOS / SwiftUI / MapKit / CoreLocationを前提とする一方、補助調査資料は将来のiOS・Android展開を想定してFlutter / MapLibreを候補としている。MVPの検証対象は目的地提案の価値であり、クロスプラットフォームや内蔵ナビの完成度ではない。

## ゴール

- 対象OSと最低OS版を決める。
- UI、地図SDK、位置権限、アプリ内ルート表示の粒度を決める。
- 外部ナビ連携先と失敗時動作を決める。
- 不採用案と再検討条件を記録する。

## 本文

### ステータス

採用。2026-09-23にプロダクトオーナーが承認した。

### 決定

| 項目 | 決定案 |
|---|---|
| 対象端末 | iPhone |
| 対象OS | iOS 17.0以上 |
| UI | Swift / SwiftUI |
| 地図 | MapKit |
| 位置情報 | CoreLocation |
| 位置権限 | `When In Use` のみ |
| 権限要求 | 初回起動時ではなく、「現在地から探す」を押した時 |
| アプリ内地図 | 候補ピン、選択中Spot、往復の概要ルート表示まで |
| 走行案内 | アプリ内では行わず外部ナビへ委譲 |
| 外部ナビ | MVPはApple Mapsのみ |
| 連携内容 | 目的地座標と表示名。経由地・複数ルートは渡さない |
| 起動失敗時 | 住所または緯度経度のコピーを提示 |

### 判断理由

- iOSのみのMVPでは、SwiftUIとMapKitが最少の実装・審査・QA範囲になる。
- MapKitは候補ピンと概要ルートというMVP要件を満たし、別の地図レンダラを導入する価値がまだない。
- 外部ナビをApple Mapsに限定すると、アプリ有無の分岐、URL Scheme差異、追加のQAを避けられる。
- `When In Use` のみとし、バックグラウンド位置情報や常時追跡を不要にすることで、プライバシーと審査上の説明範囲を抑える。
- iOS 17.0以上は、MVPの実装負担を抑えつつ旧端末を過度に切り捨てない初期基準とする。

### アプリ内ルート表示

- 候補詳細で、現在地からSpotまでと現在地へ戻る概要ポリラインを表示する。
- ターンバイターン、音声案内、走行中リルート、車線案内、オフライン地図は提供しない。
- 表示ルートと外部ナビが選ぶルートが異なる可能性を明示する。
- ルート取得失敗時は推定時間を新規計算できないため、その候補を推薦結果から除外する。表示後に失敗した場合は再試行を提示する。

### 位置情報と権限

- 目的は現在地を出発・帰着地点とした候補検索に限定する。
- 権限拒否時は、必要理由、再試行、設定アプリへの導線を表示する。
- MVPでは任意地点入力を権限拒否時の代替にしない。
- バックグラウンド位置取得、生GPS軌跡、常時監視を実装しない。
- 精度、サーバ送信、保持期間はRD-11で確定する。

### 外部ナビ連携

1. ユーザーが候補詳細で「ここに行く」を選ぶ。
2. 安全上の注意と、外部ナビで最新ルート・規制を確認する旨を表示する。
3. Apple Mapsへ目的地の座標と名称を渡す。
4. 起動要求が成功した場合に `route_started` を記録する。
5. 起動できない場合はイベントを記録せず、住所または座標のコピーを提示する。

### 不採用案

#### Flutter

MVPでは不採用。Androidを同時提供しないため、クロスプラットフォーム化の便益よりiOS固有機能との統合・検証範囲が増える影響が大きい。

再検討条件:

- Android版を同一四半期に提供する事業判断が承認された。
- iOS版で提案型UXの継続価値が確認された。
- 既存SwiftUI資産を維持する案との工数比較を行った。

#### MapLibre

MVPでは不採用。オフライン地図、独自ベクトルタイル、複雑なレイヤ表現が必須ではない。

再検討条件:

- MapKitで必要な表示または利用条件を満たせない。
- オフライン地図か独自タイル配信がP0要件になる。
- Android対応と地図表現の共通化が必要になる。

#### Google Maps外部連携

MVPでは不採用。Apple Maps連携で仮説検証に必要な走行開始導線を満たせる。

再検討条件:

- βでGoogle Maps指定の要望が複数ユーザーから得られる。
- Apple Maps連携が対象地域で重大な品質問題を起こす。
- アプリ有無の分岐とフォールバックを含むQA工数を確保できる。

#### アプリ内ターンバイターンナビ

MVPでは不採用。提案価値の検証と独立して実装・安全・運用コストが大きいため、外部ナビへ委譲する。

再検討条件:

- 外部ナビへの離脱が主要ファネルを阻害している証拠がある。
- ナビ機能が継続利用や収益化の主要因だと検証された。
- 走行中UI、安全、バックグラウンド処理、経路品質を運用できる体制がある。

### 処理フロー

```text
現在地から探す
  → When In Use権限確認
  → 現在地取得
  → 条件入力・推薦
  → MapKitで候補ピン／概要ルート
  → ここに行く
  → Apple Mapsへ目的地を引き渡す
```

### インターフェース

- 入力: 現在地、Spotの緯度経度、Spot表示名。
- 出力: MapKit上の候補表示、概要ポリライン、Apple Maps起動結果。
- 外部ナビへ渡す情報は目的地に限定し、推薦APIの内部経路IDに依存させない。

### 依存関係

- RD-05: 権限要求、候補、詳細、外部ナビ起動の画面フロー。
- RD-06: 概要ルートと所要時間の取得契約。
- RD-09: ルーティングエンジンとMapKit表示用ジオメトリ。
- RD-11: 位置情報、外部送信、イベントの保存方針。

### 注意点

- Apple Mapsが選ぶ走行ルートと、推薦時のルーティングエンジンの経路・ETAは一致しない可能性がある。
- 二輪通行可否や最新規制を完全には保証できない。現地標識と外部ナビの最新情報を優先する。
- iOS最低版は実装開始時のXcode・依存ライブラリ要件と、β参加者の端末分布で再確認する。
- 本ADRを変更する場合は、再検討条件に該当する根拠と移行影響を記録する。
