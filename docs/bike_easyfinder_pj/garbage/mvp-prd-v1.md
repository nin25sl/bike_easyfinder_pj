# バイク目的地提案アプリ MVP PRD v1

> **目的とゴールの違い**
>
> - **目的** = Why（なぜこのMVPを実施するか）
> - **ゴール** = Done 条件（何を測定し、どの状態なら次へ進むか）

## 目次

<inline-toc preview="3"></inline-toc>

## 目的

福岡周辺のiPhoneユーザーが、検索や比較に時間を使わず、「今から使える時間」と興味に合う日帰りツーリング先を決められるかを検証する。

## 背景

既存の検索型・地図型サービスに対し、本プロダクトは時間制約を先に受け取り、時間内に往復できる候補を提案する。MVPではナビ機能の完成度ではなく、提案型UXが実際の出発意思につながるかを検証する。

本書は `RD-01`〜`RD-03` の決定記録を兼ねる。`RD-04` の技術判断は `adr-001-mobile-map-navigation.md` を正とする。

## ゴール

- 対象ユーザー、検証仮説、リリース形態、検証期間、募集人数を一意にする。
- 主要KPIと成功・再検証・中止の基準を、イベントから計算可能な形にする。
- UC01〜UC03の正常系と主要例外の期待動作を定義する。
- 各機能を `MVP必須`、`条件付き`、`MVP後` に分類し、アプリの責任境界を明確にする。

### RD-01 検証仮説・成功指標・リリース対象

#### 対象ユーザー

- 福岡市および周辺から日帰りツーリングをするiPhoneユーザー。
- 仕事終わりや休日に2〜4時間程度走りたいが、行き先決定を負担に感じる人。
- MVPでは年齢、車種、排気量、経験年数による対象限定を行わない。

#### 解決する場面

「走れる時間は決まっているが、検索・比較して行き先を決めるのが面倒」という出発前の場面を解決する。走行開始後のナビゲーションは外部ナビの責任範囲とする。

#### 検証仮説

> 福岡周辺のiPhoneユーザーにとって、検索結果を自分で比較するより、利用可能時間と興味から時間内候補を提案される方が、短時間で目的地を決めて出発しやすい。

#### リリース形態

- TestFlightによる招待制の限定β。
- 募集人数: 30人。
- 検証期間: 4週間。
- 判定に用いる最小母数: 有効な推薦セッション100件。4週間で100件に満たない場合は最大2週間延長し、数値だけで中止判定しない。
- 一般App Store公開は、限定βの継続判定とプライバシー・障害対応のリリースゲート通過後に判断する。

#### ファネルとイベント定義

```text
recommendation_view
  → spot_selected
  → route_started
```

- `recommendation_view`: 候補が1件以上表示された推薦セッションごとに1回。
- `spot_selected`: 同一セッションで「ここに行く」が押された場合に1回。候補詳細の閲覧だけでは計上しない。
- `route_started`: 外部ナビへの引き渡し操作が成功した場合に1回。
- 同一セッション内の再試行は、各転換率の分母・分子に重複計上しない。
- 候補0件、位置権限拒否、API失敗は品質指標には含めるが、主要ファネルの分母から除外する。

#### KPIと判定基準

主要KPIは `route_started / recommendation_view` とする。

| 指標 | 成功 | 再検証 | 中止候補 |
|---|---:|---:|---:|
| `spot_selected / recommendation_view` | 35%以上 | 20%以上35%未満 | 20%未満 |
| `route_started / recommendation_view` | 20%以上 | 10%以上20%未満 | 10%未満 |
| 候補表示成功率 | 95%以上 | 90%以上95%未満 | 90%未満 |
| 候補表示時間 p95 | 5秒以内 | 8秒以内 | 8秒超 |

- 成功: 主要KPIが成功閾値を満たし、重大な安全・データ品質問題がない場合はMVP実装と対象拡大を継続する。
- 再検証: UX、候補品質、募集導線のどこがボトルネックかをインタビューとイベントで特定し、2週間以内の改善実験を1回行う。
- 中止候補: 有効な推薦セッション100件以上で主要KPIが10%未満、かつインタビューでも提案型UXの価値が支持されない場合は、実装拡大を止めて仮説または対象を見直す。
- 数値のみで即時撤退せず、安全上の重大問題、データ利用条件違反、運用不能が判明した場合は母数に関係なく停止する。

#### 判断日

- β開始日は実装計画確定時に設定する。
- 継続・再検証・中止の判断日は「β開始から4週間後」。母数不足時は最大6週間後とする。
- 日付が確定したら本節に絶対日付を追記する。

### RD-02 主要ユースケースと利用条件

#### 共通業務ルール

- 出発地と帰着地は現在地とし、同一地点へ戻る日帰り往復に限定する。
- 必須入力は現在地、利用可能時間、興味、高速道路利用可否。
- 興味は1件以上選択する。迷うユーザー向けに `おまかせ` を1選択肢として提供する。
- 利用可能時間は分単位で保持し、MVPの選択肢は `1時間 / 2時間 / 3時間 / 4時間 / 半日（6時間） / 1日（10時間）` とする。
- 任意出発地点、帰着時刻指定、排気量、給油、食事、車両プロフィールはMVP後とする。
- 候補は最大5件。条件を満たす候補が5件未満の場合は件数を埋めるために時間条件を緩和しない。
- 時間内判定は `往路 + 滞在 + 復路 + 帰着余裕` で行う。帰着余裕の値はRD-06で確定する。

#### UC01 仕事終わりに2時間走る

開始条件:

- ユーザーが「現在地から探す」を選択し、位置情報を取得できる。
- 利用可能時間に2時間、興味、高速利用可否を入力する。

正常系:

1. 2時間内に往復可能な候補を最大5件表示する。
2. ユーザーは候補の理由、合計所要時間、帰着予想、注意情報を確認する。
3. 「ここに行く」から外部ナビへ目的地を渡す。

終了条件: 外部ナビの起動成功、またはユーザーが候補選択を終了する。

#### UC02 休日午前に4時間走る

開始条件はUC01と同じで、利用可能時間を4時間とする。正常系では興味一致に加え、時間内でより多様な候補を提示する。終了条件はUC01と同じ。

#### UC03 目的を指定して走る

開始条件はUC01と同じで、ユーザーが `海 / 景色 / 山 / ワインディング / カフェ / 食事 / 温泉 / 道の駅 / 夜景 / 歴史・観光` から1件以上選ぶ。正常系では一致したタグと推薦理由を候補に明示する。終了条件はUC01と同じ。

#### 共通例外と期待動作

| 例外 | 期待動作 |
|---|---|
| 位置情報が未決定 | 「現在地から探す」を押した時点で `When In Use` を要求する |
| 位置情報を拒否 | 必要理由と設定アプリへの導線を表示する。手入力地点への迂回はMVPでは提供しない |
| 一時的に位置取得失敗 | 再試行を提示し、前回位置を無断利用しない |
| 候補0件 | 時間、興味、高速可否を変更する導線を表示し、条件を自動緩和しない |
| 推薦API失敗・タイムアウト | 安全に再試行できるエラーを表示し、古い候補を新規結果として表示しない |
| 一部候補の経路取得失敗 | 当該候補を除外し、残る候補を表示する。全件失敗なら候補0件とは区別して障害表示する |
| 外部ナビを起動できない | 目的地住所または座標をコピーできるフォールバックを表示する |

### RD-03 MVPスコープと責任境界

#### MVP必須

- 初回説明と、利用操作に起因する位置権限要求。
- 現在地、利用可能時間、興味、高速利用可否の入力。
- 条件を満たす候補最大5件のカードまたは一覧表示。
- 候補詳細、地図上の候補ピン、概要ルート、推薦理由、予測所要時間、情報鮮度の表示。
- `興味あり / 興味なし / 訪問済み / ここに行く` の行動記録。
- 外部ナビへの目的地引き渡し。
- 匿名端末IDによる最小限のイベント計測。
- 候補0件、権限拒否、タイムアウト、部分障害の表示と再試行。
- 走行中の複雑操作を促さない注意表示。走行中利用を前提としたUIは提供しない。

#### 条件付き

| 機能 | 採用条件 | 判断期限 | 不採用時の動作 |
|---|---|---|---|
| 天気警告 | 利用条件と月額上限内のProviderをRD-10で選定できる | RD-10承認時 | 初回対象外と明示し、外部ナビ等で確認を促す |
| 道路規制警告 | 信頼できる取得元、更新間隔、障害時動作をRD-10で確定できる | RD-10承認時 | 初回対象外と明示し、現地標識と外部ナビを優先させる |
| Google Maps連携 | 追加対応の価値が実装・QAコストを上回るとRD-04で判断する | ADR-001承認時 | Apple Mapsのみ提供する |

#### MVP後

- アカウント、複数端末同期、任意出発地点、帰着時刻指定、車両・排気量プロフィール。
- アプリ内ターンバイターンナビ、オフライン地図、リアルタイム渋滞最適化。
- 給油・食事を旅程へ組み込む機能、複数日ツーリング、予約。
- Android、iPad最適化、CarPlay / Android Auto。
- UGC、SNS、通知、ML / LLM推薦。

#### 責任境界

```text
アプリの責任
  現在地取得 → 条件入力 → 候補提案 → 詳細・概要ルート確認 → 目的地引き渡し

外部ナビの責任
  最新ルート選択 → 走行案内 → 走行中の経路変更 → 到着
```

- 所要時間と帰着予想は予測であり保証しない。帰着余裕と鮮度を表示する。
- 交通規制・天候・現地標識は最新情報を優先し、アプリ表示のみで走行可否を判断させない。
- 外部ナビ起動後の走行完了や帰着時刻は、MVPでは自動追跡しない。

### インターフェース

主要イベントと推薦APIの詳細はRD-06で確定する。本書では画面・計測上の意味だけを定義し、フィールド名やHTTP契約を先行固定しない。

### 依存関係

- RD-04: モバイル、地図、位置権限、外部ナビ方式。
- RD-05: 画面フロー、低忠実度モック、UI受入条件。

### 注意点

- KPI閾値は事業上の正解値ではなく、限定βで継続判断を行うための初期基準である。
- `route_started` は実際の出発や完走を保証しない。βでは定性インタビューを併用する。
- 候補0件を減らすために時間条件を暗黙に緩めない。
- 承認済みの基準を変更する場合は、変更理由、影響するRD、承認日を記録する。
