## RD-05 UX・画面フロー

- 検索結果一覧を主導線にせず、候補を1件ずつ示すカード型・逐次提案UXとする。
- 初回は「アプリ説明→現在地利用→利用可能時間→興味・やりたいこと→高速道路利用可否→スポット提案」を基本とする。
- 2回目以降は前回条件の利用または条件変更から短い導線で提案へ進める。
- リアクションは「興味あり」「興味なし」「行ったことがある」とし、興味あり一覧を用意する。
- 「興味なし」は永久除外またはHard Filterにせず、同一Spotと類似カテゴリ・タグの推薦スコアを下げる要素として扱う。

## RD-06 推薦・API

- `往路時間 + 滞在時間 + 復路時間 + 帰着余裕15分 <= 利用可能時間` を時間条件とする。
- MVP APIはRecommendation、Interaction、Privacyの3領域に整理する。
- 各APIの目的、入力、出力、呼出元画面、呼出タイミングを把握できる構成とする。
- リアクションをRecommendationへ反映し、「興味なし」は順位を下げる要素とする。

## RD-07 Spot・taxonomy・収集

- MVP公開対象は九州7県。福岡周辺100件程度は初期テストと収集方式検証に使う。
- 固定件数より、九州全域から継続的にSpotを収集・更新できる仕組みを優先する。
- 一般Webも候補発見に利用できる。営業時間、閉業、駐車場、二輪可否などの変動情報は信頼性の高い情報源で確認する。
- 1 Spotに複数カテゴリを付与できる。taxonomyは実データ収集・分析後に確定する。

## RD-08 Spot・Source・Freshness

- Canonical SpotとSourceを分離する。
- Canonicalの各属性について採用Sourceを追跡可能にする。
- 100m以内かつ名称類似度0.8以上を重複候補とし、自動統合せずレビューする。
- Canonical SpotとSourceは月1回の更新チェックを基本とする。月次チェック周期と属性別Freshness期限は別に管理する。

## RD-09 所要時間・外部Map

- アプリ内の実走行ルート検索とターンバイターンナビゲーションは実装せず、目的地提案までを責任範囲とする。
- 走行時はApple Maps、Google Maps、その他対応可能な外部Mapへ引き渡す。
- 推薦用に距離と所要時間を取得する。iOSだけに依存せず、将来のAndroid対応も考慮したProvider構成とし、比較・検証後に決定する。
- ValhallaはMVP必須としない。ワインディング優先、海沿い優先、市街地回避など独自ルーティングが必要になった場合に再検討する。

## RD-10 Weather・安全表示

- 天気は推薦順位と候補除外に使用しない。
- 天気は利用者が行くかを判断するための注意情報として表示する。
- 悪天候でもアプリ側でSpotを自動除外しない。天候依存Spotは詳細等で注意を表示する。

## RD-12 インフラ・費用・Release

- local、staging、productionの3環境を使用する。
- stagingとproductionは同一アーキテクチャを基本とし、スペック差は許容する。ドメイン、DB、シークレット、API endpoint、スペック、外部サービス設定等は環境差分として管理する。
- 暫定性能目標はRecommendation API p95 5秒以内、初回候補表示約3秒とする。増加後はCPU、Memory、DB負荷、API Response Time等の実測値で調整する。
- 日次バックアップ、7世代以上保持、月1回リストア試験を基本とする。
- 外部API・インフラのMVP費用目標は月額10,000円以内。低コスト・最小構成を優先し、超過する構成変更は再検討する。

## 基本設計への引継ぎ

- ホスティング、DB、監視、バックアップの具体的サービス・構成
- staging / production環境差分

- 九州7県の試験件数、代表テストケース、リリース合格条件
- バックアップ対象別の復旧優先度、RPO / RTO
- 再収集可能データとバックアップ復旧必須データの区分
- 月額10,000円以内で成立する具体的インフラ構成
- 推薦用の距離・所要時間Providerおよび外部Map連携の具体仕様
- 天気Provider、注意表示条件・文言
