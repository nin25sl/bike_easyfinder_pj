# RD-05：画面フロー / UX

## 決定事項

- **承認済み。**
- Bike EasyFinderは検索結果一覧を主役にせず、**Tinder等のマッチングアプリを参考にしたカード型・逐次提案UX**を軸とする。
- 初回起動は、説明 → 現在地利用 → 利用可能時間 → 興味 → 高速道路可否 → カード提案、の順を基本とする。
- 2回目以降は、前回条件を再利用してすぐ提案へ進める導線と、条件変更導線を用意する。
- カードに対する主要リアクションは以下とする。
  - 興味あり
  - 興味なし
  - 行ったことがある
- 「興味あり」は後から一覧で確認できる。
- 「興味なし」は**永久除外しない**。同一Spotおよび類似カテゴリ・タグに負の嗜好シグナルを与え、以後の推薦で**出にくくするソフト抑制**として扱う。
- 負の嗜好シグナルはハードフィルタにせず、時間経過、候補不足、別条件、後続の「興味あり」等によって再提案可能とする。
- 具体的な減点幅、減衰期間、類似カテゴリ判定方法は基本設計で決定する。
- 「行ったことがある」は訪問済み情報として保持し、推薦ロジックに利用する。
- Apple Maps / Google Maps等へ遷移する前に必要なユーザー状態を保存する。

## 基本設計への引継ぎ

- カードの情報量、スワイプ方向、ボタン操作、アニメーション、誤操作Undoを設計する。
- 「興味なし」によるSpot単位・カテゴリ単位・タグ単位の負の重みと減衰ロジックを決定する。
- 興味あり一覧の表示項目、並び順、削除・再評価導線を決定する。
- 初回／再訪時の前回条件再利用ルールを決定する。
- RD-10の安全確認表示を外部Map遷移直前のUXと整合させる。

## ステータス

**承認済み・基本設計へ移行**

# RD-06：推薦ロジック / API

## 決定事項

- **承認済み。**
- 時間条件は `往路 + 滞在 + 復路 + 帰着余裕15分 <= 利用可能時間` をMVPの基本ハード条件とする。
- APIは個別APIだけでなく、MVP全体の役割を把握できる構成にする。
- 公開APIは原則として以下の3領域に整理する。
  - Recommendation
  - Interaction
  - Privacy
- MVPではアカウントを必須とせず、匿名installation ID単位でユーザー状態を保持する。
- RD-05の「興味なし」は永久除外ではなくソフト抑制とし、Recommendation側でスコアへ反映する。
- MVPスコープと将来スコープをAPI契約上でも明示する。

## 基本設計への引継ぎ

- OpenAPI v1、エラーコード、タイムアウト、冪等性、バージョニングを確定する。
- Interactionイベントの発火条件と重複計上防止を定義する。
- 推薦結果0件、外部Provider障害、タイムアウト時のレスポンスを定義する。
- 帰着余裕15分を将来ユーザー設定化するかはMVP後に再評価する。

# RD-08：データモデル / Source / Freshness / 行動イベント

- 行動イベントはRD-05の承認内容に合わせ、`shown / interested / not_interested / visited / selected / route_started` を基本イベント候補とする。詳細な発火条件・重複計上防止は基本設計で確定する。

# RD-09：移動時間推定 / 外部Map連携

## 決定事項

- **方針承認済み。**
- Bike EasyFinder内ではルート検索・ターンバイターンナビゲーションを行わず、責任範囲を「ツーリング先の提案」までとする。
- 実走行のルート検索・ナビゲーションはApple Maps / Google Maps等の外部Mapへ委譲する。
- 推薦判定のための距離・所要時間はBike EasyFinder側で取得する。
- 推薦用所要時間Providerは、**iOS / AndroidのクライアントOSに依存せずBackendから利用できるAPI**を採用条件とする。
- 外部にインストールされたMapアプリそのものを推薦時ETA取得元にはしない。外部Mapアプリはナビ開始時の遷移先として利用する。
- Apple Maps Server API、Google Routes API、その他のサーバー向けRouting APIをPOC比較対象とし、精度・料金・利用条件・障害時動作で選定する。
- Valhallaと独自ルーティングはMVP対象外。独自のワインディング優先等が必要になった段階で再評価する。
- POC / Ver0.1確認対象は九州7県とする。

## 基本設計への引継ぎ

- Provider比較表を作成し、九州7県のPOCで採用Providerを決定する。
- ETA取得はBackend経由とし、iOS/将来Androidで同じ推薦結果を利用できる境界にする。
- 推定ETAと実際に外部Mapで表示されるETAの許容差を決定する。
- Provider障害時のフォールバック、キャッシュ、タイムアウトを決定する。
- Apple Maps / Google Mapsへの目的地座標・Spot名・必要なパラメータの受け渡し仕様を確定する。
- 外部Mapが未インストールの場合のフォールバックUXを確定する。

## ステータス

# RD-10：天気 / 道路情報 / 安全表示

## 決定事項

- WeatherKitはMVPで利用する。
- MVPでは**天気を推薦ランキング計算には使わない**。
- 天気はスポット詳細表示時の注意情報として使う。
- 天候条件に依存するスポット属性を持たせる方向とする。
  - 例：晴れ向き
- 天候依存属性があるスポットでは、詳細表示時にWeatherKitを確認し、必要なら注意ポップアップを表示する。
- 天候が悪くてもスポットを自動除外しない。
- 実際に行くかどうかはユーザー判断に委ねる。
- リアルタイム道路規制はMVPだけでなく、本番でもアプリ側の対象外とする。
- 道路規制・実走行ルートはGoogle Maps / Apple Maps / 現地標識に任せる。
- 安全確認表示は**外部Mapへの遷移前**に行う。
- ユーザー画面への「最終確認時刻」表示は行わない。
- Freshness管理自体は内部で継続する。

# RD-11：プライバシー / 分析 / アカウント

  - 課金
  - Web版

  - 履歴引き継ぎ
- MVP時点のinstallation IDベースのデータを、将来user_idへ紐付け可能な構造にする。
- 正確な現在地はアプリ利用時に取得し、推薦処理のみに利用する。
- 正確な現在地は永続保存しない。
- 行動イベントの具体的な定義はRD-05修正後に再判断する。
- 利用分析は全ユーザーを基本対象とする。
- Appleの規約に沿い、以下を満たす。
  - 収集目的を明示
  - 初回に同意取得
  - 同意撤回手段を提供
  - App Store Connectで正しく申告
- 広告・クロスアプリトラッキングには利用しない。
- データ保持期間は一律にせず、保存対象データごとに個別に決める。
- 具体的な保持期間はプロダクトオーナー最終承認前の提案として以下を採用候補とする。
  - 正確な現在地: 永続保存しない。推薦リクエスト処理中のみ利用する。
  - Recommendation Impression / shown: 生データ90日、集計後データ12か月。
  - interested / not_interested / visited / selected / route_started: 最終利用から24か月。ユーザー削除要求時は即時削除対象。
  - アプリ分析イベント: 生データ12か月。
  - API / Applicationログ: 30日。
  - Crash / Errorログ: 90日。
  - Privacy同意状態: installationが有効な間保持。削除時はユーザーデータとともに削除し、必要な最小限の削除処理監査情報のみ別管理する。
  - Backup内の削除対象データ: バックアップ保持世代の失効に伴い最大7日程度で消去される設計を基本とする。
- MVPでは匿名ユーザーデータ削除機能を実装する。
- installation IDに紐づく生データを削除できるようにする。
- 現行の削除トークン方式をMVPで採用してよい。
